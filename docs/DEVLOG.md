## S0 · 项目骨架与开发规范（2026-09-30）

**问题**：从空仓库开始，要先定好目录结构、依赖、配置方式和提交规范，后面每个阶段才能往里填。

**做法**
- 目录采用“平铺包”结构：`simul_interp/` 直接放在仓库根目录，不装包也能用 `python -m simul_interp` 运行，对初学者最直观。
- 配置分三层：代码默认值 → `config.toml` → 命令行参数。写错配置项名会直接报错，避免拼错了却悄悄不生效。
- API 密钥只放在 `.env` 或环境变量里，`config.toml`、`.env`、音频文件、会话记录都写进 `.gitignore`，防止把密钥和隐私内容推到 GitHub。
- 依赖用 `requirements.txt` 的平台标记（`; sys_platform == "darwin"`）区分 macOS 和 Windows，一份文件两边通用。
- 本机开发环境：用 `ml` conda 环境的 Python 建 `.venv --system-site-packages`，复用已装好的 torch / mlx-whisper，只把新依赖装进项目自己的环境，不污染 `ml`。

**主要文件**：`simul_interp/config.py`、`simul_interp/__main__.py`、`config.example.toml`、`.env.example`、`requirements.txt`、`.gitignore`、`CLAUDE.md`

**验证**：`python -m pytest` 通过配置相关的 4 个测试；`python -m simul_interp config` 能打印生效配置。

**开工前的测量**：完整版 whisper-large-v3（MLX）在 M5 上识别一次约 0.83～0.93 秒，基本与音频长短无关（Whisper 总是把输入补齐到 30 秒）；打开逐词时间戳会再多约 0.4 秒。所以后面的流式识别不用逐词时间戳，改用 Whisper 自带的分段时间戳。

**经验**：先做一次粗测再设计。这 1 秒的固定开销直接决定了“每隔多久识别一次”和整体能做到多低的延迟。

## S1 · macOS 内录系统声音（2026-09-30）

**问题**：要录到“电脑正在播放的声音”（会议软件、浏览器），同时不能影响用户用耳机或扬声器听原声，也不想让用户装虚拟声卡。

**做法**
- 自己写了一个约 250 行的 Swift 小程序 `native/macos/si_audio_tap.swift`，用 macOS 14.2+ 的 Core Audio Taps：
  1. `CATapDescription(monoGlobalTapButExcludeProcesses: [])`：把所有进程的声音混成一路单声道；
  2. `muteBehavior = .unmuted`：只复制不静音，原声照常播放（这就是不需要“多输出设备”的原因）；
  3. tap 不能直接读，要挂到一个**只包含这个 tap** 的私有聚合设备上，再注册 IOProc 回调取数据；
  4. 用 `AVAudioConverter` 从 48 kHz 重采样到 16 kHz，以 float32 写到 stdout；日志用 JSON 写到 stderr。
- 没有直接用 audiotee：它没有声明开源许可证，不能放进仓库；读它的代码学用法，自己实现更可控。
- 默认输出设备变化（插拔耳机、连蓝牙）时，小程序以退出码 3 退出，Python 端立刻重启它，重新挂到新设备上。
- Python 端 `simul_interp/audio/`：统一的 `AudioSource` 基类把任意长度的数据切成 512 点（32 ms）的小块并打上“音频流时间”；`record` 命令用来检查内录。

**踩坑：没权限时系统不报错，只给静音**
- 第一次测试收到的数据量完全正常（每秒 16000 个采样点），但全部是 0。
- 原因：macOS 把“系统录音”权限记在**负责进程**头上，也就是启动它的应用。当时是 Claude 应用在后台启动它，Claude 没有申请这项权限，所以既不弹窗也拿不到声音。
- 解决：小程序启动后用 `responsibility_spawnattrs_setdisclaim` 重新启动自己，声明“我自己负责”，同时把带 `NSAudioCaptureUsageDescription` 的 Info.plist 用 `-sectcreate` 嵌进可执行文件。之后系统以 si-audio-tap 的名义弹出权限框，从终端、VS Code 还是别的应用启动都一样。
- 排查方法：程序卡住时用 `sample <pid>` 看调用栈，发现停在创建 tap 的调用里、并且加载了 TCC（权限）框架，从而确认是在等权限弹窗。
- 重新编译会让 macOS 把它当成新程序、可能再要一次权限，所以 Python 端按**源码哈希**决定是否重新编译，而不是按修改时间。

**主要文件**：`native/macos/si_audio_tap.swift`、`native/macos/Info.plist`、`scripts/build_macos_tap.sh`、`simul_interp/audio/base.py`、`simul_interp/audio/macos_tap.py`、`simul_interp/audio/util.py`

**验证**
- 播放一段 6.9 秒的法语合成语音同时内录：音量 -14～-16 dBFS，播完后是真正的全零静音；
- 把录到的音频交给 Whisper，识别结果与原文一字不差；
- `python -m simul_interp record --seconds 9` 正常出音量条并保存 WAV；pytest 6 个测试通过。

**经验**：系统级功能先写一个最小可运行的探针，用“数据量对不对、是不是全零、内容对不对”三步验证，比一上来就接进完整流程好排查得多。

## S2 · 音频文件模拟源与测试音频（2026-09-30）

**问题**：调识别和翻译时不可能每次都开一个真实会议；用户的真实录音又涉及隐私，不能放进仓库，也不适合反复发给翻译 API。

**做法**
- `FileAudioSource`：用 ffmpeg 把任意格式解码成 16 kHz 单声道，**按真实语速**一块一块送出。每一块都等到它“播放完”的时刻才送，和真实内录一样（声音总是播完才拿得到），所以用它测出来的延迟就是真实延迟。
- 文件结束后补 1.5 秒静音，让语音检测能判断最后一句已经说完。
- `speed=0` 表示不等待、尽快送完，只用于离线单元测试。
- `scripts/make_test_audio.py`：用 macOS 自带的法语语音 Thomas 合成两段内容相同、节奏不同的测试音频，并附带逐句的标准答案：
  - `fr_meeting.wav`（62 秒）：句间停顿 0.7 秒，模拟正常发言；
  - `fr_continuous.wav`（51 秒）：几乎不停顿、语速更快，模拟“一直有人在说话”的最难情况。
- 生成的音频放在 `samples/`，已被 `.gitignore` 忽略，需要时运行脚本重新生成即可。

**主要文件**：`simul_interp/audio/file_source.py`、`scripts/make_test_audio.py`、`tests/test_file_source.py`

**验证**：新增 2 个测试，一个检查切块和补静音，一个检查按实时速度送出（0.5 秒音频约 0.5 秒送完，且每块都在播放完之后才送）；pytest 共 8 个通过。

**经验**：测试数据要“可重复、无隐私、有标准答案”。合成语音不如真人录音难，但足够用来调流程和测延迟；准确率最终还要用真实录音在本地检验。

## S3 · 语音检测与分段（2026-09-30）

**问题**：Whisper 不能一直对着所有声音跑：没人说话时浪费算力，还容易在静音上“幻觉”出不存在的句子（比如凭空出现“谢谢观看”）。同时需要尽快知道“一句话说完了”，这是降低延迟的关键。

**做法**
- 用 Silero VAD（随 pip 包附带的约 2 MB 小模型，只判断有没有人声，不做转写），每 32 毫秒给出一个说话概率。
- 判断逻辑写成与模型无关的状态机 `VadSegmenter`，输出“开始 / 音频 / 结束”三种事件：
  - **迟滞双阈值**：概率 ≥ 0.5 才算开始说话，说话中低于 0.35 才开始计静音，避免在阈值附近反复开关；
  - **静音 400 毫秒**判定一句结束（向上取整成 13 块，保证至少 400 毫秒）；
  - **句首预留 200 毫秒**：开始说话前的几块也一起送给识别，避免吞掉第一个音；
  - 说话中的静音块照样送给识别，因为词尾常常落在这些块里。
- `vad` 命令：只跑语音检测并打印每段起止时间，用来调参数。
- 全局 `--file / --speed` 参数：任何命令都可以改用音频文件作为输入。

**主要文件**：`simul_interp/vad.py`、`tests/test_vad.py`、`simul_interp/__main__.py`

**验证**
- 4 个状态机测试（预留与结束时机、短停顿不切句、迟滞、收尾），pytest 共 12 个通过；
- `fr_meeting.wav` 正好切出 10 段，与 10 句话一一对应；
- `fr_continuous.wav` 整段 51 秒被当成一段（没有超过 400 毫秒的停顿），说明后面的流式识别**不能只靠停顿来定稿**；
- 每块检测耗时 0.11 毫秒，可以忽略。

**经验**：把“模型”和“判断逻辑”拆开。逻辑部分用构造的概率序列就能精确测试；另外注意 Python 的 `round(12.5) == 12`（四舍六入五成双），涉及“至少多长”时用 `math.ceil`。

## S4 · Whisper 流式识别（2026-09-30）

**问题**：Whisper 一次只能处理一整段音频，本身不会“边听边出字”；而且识别一次固定要约 0.8 秒，只看一次结果也不可靠（截在词中间的 3 秒音频曾被识别成 “l'électro-électriq”）。

**做法：LocalAgreement（参考 ufal/whisper_streaming 的思路，按本项目需要重写）**
- 说话期间每隔约 0.6 秒，把缓冲区（这句话到目前为止的音频）整段重新识别一次；
- **本次和上一次开头一致的部分才“确认”**，确认后不再改，可以送去翻译；不一致的尾巴是“暂定”，只用来灰字显示；
- 已确认的词**只追加、不替换**：Whisper 偶尔会把已确认的词换个写法甚至漏掉，用编辑距离把新结果和已确认部分对齐，而不是要求逐字相同，这样既不会重复发出，也不会丢词；
- **切缓冲区**：一整句确认完（Whisper 分段以句号、问号结尾）就切掉这段音频，已确认的文字作为提示词带给下一次，缓冲区一直很短、每次识别都快；
- **VAD 判定说完时**：如果上一次识别已经覆盖到说话结束，直接确认剩下的尾巴，省一次识别（约 0.8 秒）；
- 模型只从本地缓存加载（传本地路径给 mlx_whisper），找不到就报错，不会自动下载。

**用数据驱动的三次改进**（新增 `bench-asr` 命令：按真实语速跑测试音频，用一次离线的逐词时间戳识别作参照，统计每个词的显示延迟和确认延迟）
1. 长句没有句号时缓冲区越积越长，单次识别从 0.7 秒涨到 1.4 秒，还出现过一次 3.3 秒的强制切分。
   → 缓冲区超过 6 秒时，识别顺带输出逐词时间戳，直接切在已确认的逗号或词后面。
2. 音频很短时 Whisper 会“编下去”，把提示词里的上一句接着复述一遍（灰字里闪过错字）。
   → 加语速上限（每秒最多 6 个词，超出就截掉）；一句话开头、音频不到 1.5 秒时先不给提示词。
3. 逐词时间戳会把法语的省音和连字符拆开（d'être → “d” + “'être”，Est-ce → “Est” + “-ce”），导致前后两次结果对不上，确认被拖慢。
   → 没有前导空格的片段并回前一个词，与 `text.split()` 的分词保持一致。

**结果**（M5，完整版 large-v3，两段 60 秒左右的法语合成语音）

| 指标 | fr_meeting（句间有停顿） | fr_continuous（几乎不停顿） |
|---|---|---|
| 显示延迟（中位数 / 90%） | 0.98 / 1.64 秒 | 1.31 / 2.05 秒 |
| 确认延迟（中位数 / 90%） | 1.75 / 2.62 秒 | 2.30 / 3.09 秒 |
| 句末延迟（中位数） | 1.70 秒 | 2.46 秒 |
| 单次识别平均 / 最慢 | 0.73 / 1.57 秒 | 0.93 / 1.56 秒 |
| 暂定文字里的错词 | 25%（改进前 29%） | 16%（改进前 19%） |
| 词错误率 WER | 5.6% | 5.6% |

WER 里剩下的主要是数字写法（douze → 12、sept pour cent → 7%），意思没有错；确认下来的全文没有重复、没有丢词。

**主要文件**：`simul_interp/asr/streaming.py`、`simul_interp/asr/mlx_backend.py`、`simul_interp/asr/runner.py`、`simul_interp/bench.py`、`tests/test_streaming.py`

**验证**：6 个流式识别测试用“假识别后端”按剧本返回结果，并故意把正说到一半的词截断，覆盖“两次一致才确认”、整段不重复不丢词、切缓冲区、复用上一次结果、无句号时强制切分；pytest 共 18 个通过。

**经验**
- 先把“怎么衡量”做出来（`bench-asr`），每次改动都用同一把尺子量，改进才有方向。第一版的问题（长句变慢、灰字幻觉、法语省音被拆开）都是看数据看出来的。
- MLX 的计算流按线程区分，模型的加载和每一次识别必须在同一个线程里，所以加载放在识别线程里做。

## S5 · 流式翻译（2026-09-30）

**问题**：确认下来的法语要尽快变成中文：既不能一个词一个词地翻（没有上下文、翻不准），也不能等整段说完再翻（太慢）。

**做法**
- `ChatTranslator`：调用任何兼容 OpenAI Chat Completions 的接口，直接用 httpx 解析 SSE 流（`data: {...}` 一行一条，`[DONE]` 结束），不依赖 openai SDK，也能看清流式接口到底是怎么回事。
- **什么时候送去翻译**（`UnitBuilder`，纯逻辑、可单测）：遇到句末标点就送；句子很长时，遇到逗号且已经攒够 8 个词，先送前半句；攒到 25 个词还没有标点也送；VAD 判定说完，剩下的全送。
- **上文**：带上前 3 句原文，放在用户消息里；系统提示词保持不变，固定的开头部分能被服务商缓存，更快也更便宜。
- **预热**：启动时先 `GET /models`，建立 TLS 连接并检查密钥，第一句话不用再花握手时间；密钥无效时在开始前就报错。
- **并发**：最多同时翻 3 段，一段慢了不会堵住后面的；翻译失败只影响那一句。
- `bench-translate` 命令：逐句实测首字延迟和整句完成时间，方便比较不同服务商和模型。

**踩坑：查文档，不要凭记忆**
- 原本按记忆写了 `deepseek-chat`，实际查 DeepSeek 官方文档发现，现在最快的模型叫 `deepseek-flash`；
- 更关键的是，文档写明**思考模式默认开启**（effort 默认 high）。不关的话，每句话都要先“想”一阵才开始输出，对同传是致命的延迟。所以默认配置显式发送 `"thinking": {"type": "disabled"}`，并有单元测试守着这一条。

**主要文件**：`simul_interp/translate.py`、`tests/test_translate.py`、`simul_interp/bench.py`、`simul_interp/config.py`、`config.example.toml`

**验证**：4 个翻译测试，用 `httpx.MockTransport` 模拟服务端，检查 SSE 解析、请求内容（模型、流式、关闭思考、术语表、上文）、HTTP 错误和后台并发翻译；pytest 共 22 个通过。真实 API 的延迟要等填好密钥后用 `bench-translate` 实测。

**经验**：用 `httpx.MockTransport` 这类“假服务端”测网络代码，不需要密钥、不花钱、结果稳定，还能精确检查发出去的请求内容。

## S6 · 串起完整流程（终端版）与会话记录（2026-09-30）

**问题**：前面各阶段都是单独跑通的零件，要串成一个真正能用的程序：音频 → 语音检测 → 流式识别 → 翻译 → 显示，还要把结果存下来。

**做法**
- `Interpreter` 流水线只依赖一个很小的界面接口 `View`（`on_live` 显示正在说的话，`on_unit` 显示原文和流式译文），终端版和下一阶段的悬浮窗共用同一条流水线。
- 终端界面：每段原文、译文各打一行，并标出翻译的首字延迟和完成时间；最底下一行实时刷新“正在说的话”，灰色是还没确认的部分。
- 会话记录：每翻完一句就追加写入 Markdown，程序中途退出也不丢；几段译文并发进行、完成顺序不定，所以按原文顺序缓冲后再写。用文件做输入时命名为 `<文件名>_译文.md`，内录时命名为 `同传_<日期>_<时间>_译文.md`，已存在就不覆盖。本机配置把记录目录设为 `~/录音文件/录音译文`。
- `run` 命令：`--mock-translate` 用模拟翻译（不联网），没有密钥也能测试整条流程；没有密钥时只显示原文，不会报错退出。

**踩坑：确认下来的文字里混进了幻觉 “Merci.”**
- 第一次完整运行时，第 2、3 句之间多出一句原文没有的 “Merci.”，而且被确认、送去了翻译。
- 原因：VAD 判定说完后要再识别一次，而缓冲区末尾带着约 0.4 秒静音，Whisper 对着静音“补”了一句（典型幻觉）。这次识别不经过“两次一致”的检验，所以直接被确认了。
- 修复：最后一次识别前，把缓冲区截到停止说话后 0.2 秒。顺带发现“太短不识别”原本按缓冲区长度判断，而缓冲区包含句首预留和句尾静音，这个判断永远不会生效，改为按实际说话时长判断（阈值 0.45 秒，含 0.2 秒预留，避免误丢 “Oui.” 这类短回答）。
- 新增两个回归测试：假识别后端在句尾静音超过 0.3 秒时会“补”一句 Merci.；修复前测试失败，修复后通过。

**主要文件**：`simul_interp/pipeline.py`、`simul_interp/ui/console.py`、`simul_interp/transcript.py`、`simul_interp/asr/streaming.py`、`tests/test_transcript.py`、`tests/test_streaming.py`

**验证**：pytest 共 26 个通过；用 fr_meeting 和模拟翻译完整跑一遍，13 段原文完整、顺序正确、没有幻觉，长句在逗号处拆成两段，会话记录按顺序写好。

**经验**：单独测零件发现不了的问题（比如这个只在“说完后再识别一次”时出现的幻觉），要靠端到端跑一遍才能暴露。发现 bug 先写一个能复现它的测试，再修。

## S7a · 修复实测中发现的三个识别问题（2026-09-30）

**问题**：做悬浮窗时真实跑了几遍完整流程，又暴露出三个只在特定时机才出现的识别问题（每次运行的线程调度和识别时机都不完全一样，所以前几次没遇到）。

**1. 切在词中间，下一段开头的半个词被识别成别的词**
- 现象：确认的文字里出现了原文没有的 “heures.”。
- 原因：长句的缓冲区超过 6 秒后按 Whisper 的逐词时间戳切，而时间戳有 0.1~0.3 秒误差，切点落在了 “utilisateurs” 中间，下一段开头只剩 “-teurs” 的尾音。
- 修复：不完全相信时间戳，在切点前后 0.25 秒内找声音最小的 20 毫秒切下去；一样安静时取离原切点最近的。词与词之间的真实停顿比模型估的时间戳可靠。

**2. Whisper 陷入重复循环，一次识别花了 4.65 秒**
- 现象：识别结果是 “…de la version de la version de la version de…”，解码一直生成到默认上限 224 个 token。
- 修复：按音频长度限制最多生成的 token 数（每秒 10 个，正常语速不到 5 个），解码时间有了上限；再检测“同一个 2~4 词短语连续出现 3 次以上”，只保留第一次（单个词要连续 4 次才算，“non non non” 可能是真的）。

**3. 结尾对着静音“补”出一句（“Merci.”、“chaîne.”）**
- 原因：最后一句已经被“两次一致”确认完，但 VAD 判定说完后又对剩下的音频识别了一次，而剩下的几乎全是静音。这次识别不经过两次一致的检验，幻觉就直接被确认了。
- 第一次修复只判断了“切过缓冲区后剩下的说话不到 0.3 秒”，但句尾正好落在缓冲区末尾时切不开，又漏出一个 “chaîne.”。
- 最终判断标准：**上一次识别之后，还有没有新说的话**。上一次听到的内容都已确认、之后又说了不到 0.3 秒，就不再识别；需要识别时，只保留停止说话后 0.1 秒。

**主要文件**：`simul_interp/asr/streaming.py`、`simul_interp/asr/mlx_backend.py`、`simul_interp/asr/types.py`、`tests/test_streaming.py`

**验证**
- 新增 3 个测试：切点挪到真实停顿里、重复循环截断、“整句确认后只剩静音时不再识别”（假后端会对纯静音补一句 Merci.；临时关掉修复时这个测试失败，打开后通过）；pytest 共 29 个通过。
- 两段测试音频重跑：确认下来的全文完整、没有碎片词、结尾没有幻觉，最慢一次识别从 4.65 秒降到 2.1 秒以内。

**注意：延迟有波动**。同样的代码连续跑，fr_continuous 的确认延迟中位数在 2.2~2.7 秒之间变化。这台是无风扇的 MacBook Air，连续十几轮满负荷识别后可能发热降频（未专门验证）。长时间开会时要留意这一点。

**经验**
- 写回归测试时，先确认“去掉修复后测试会失败”，否则测试可能根本没复现问题。这次第一版测试就没复现：它喂了实际中不会出现的长静音。
- 修复要找到真正的判断标准。“切过缓冲区”只是表面条件，“上一次识别之后有没有新说的话”才是本质。

## S7b · 透明悬浮字幕窗（2026-09-30）

**问题**：开会或看视频时，字幕要浮在画面上：看得清、不挡操作、不抢焦点，全屏时也要能看到。

**做法（PySide6）**
- 外观：半透明深色圆角背景；上面一行法语原文（小字、浅灰），下面一行中文译文（大字、白色），正在流式输出的译文末尾有灰色 “…”；最底下是正在说的话，白色是已确认的、灰色是暂定的。文字加阴影，背景调得很透明时压在亮色画面上也看得清。
- 窗口：无边框、始终置顶、不接受焦点（在会议软件里打字不会被打断），显示时也不激活。
- **macOS 全屏**：Qt 没有提供“出现在所有桌面空间、浮在全屏应用上面”的设置。这里用 ctypes 直接给 NSWindow 发 Objective-C 消息（`setCollectionBehavior:`、`setLevel:`、`setHidesOnDeactivate:`），并把程序设为“辅助应用”（不在程序坞显示），不需要额外安装 PyObjC。
- 操作：拖动移动，右下角调整大小；右键菜单调字号、背景深浅、鼠标穿透、清空、退出。开启穿透后窗口本身收不到点击，所以同样的菜单也放在菜单栏图标里，用来解锁和退出。
- 位置、大小、字号、背景透明度退出时用 QSettings 保存，下次启动自动恢复。
- 线程：识别和翻译在后台线程里跑，结果以不可变的快照通过 Qt 信号交给界面线程，每 50 毫秒最多刷新一次。
- 用文件做输入时，放完 5 秒自动退出；内录要用户自己退出。

**踩坑**
- **macOS 上不能用 Qt 的 Tool 窗口类型**：它会在切换到别的应用时自动隐藏，而我们恰恰需要在别的应用处于前台时显示。Windows 上用 Tool 类型，是为了不在任务栏占位置。
- **Qt 事件循环里 Python 收不到 Ctrl+C**：事件循环在 C++ 里跑，用一个每 200 毫秒触发一次的空定时器让解释器有机会处理信号。
- **offscreen 模式下调用原生接口会段错误**：单元测试用 Qt 的 offscreen 平台，这时窗口句柄不是 NSView，对它发 Objective-C 消息会直接崩溃。改为只在 Qt 平台是 cocoa 时调用。
- **Retina 屏截图是 2 倍像素**：预览脚本拼背景图时要按 `devicePixelRatio` 换算，否则比例不对。

**看不到屏幕，怎么验证界面**
- `scripts/overlay_preview.py`：不跑识别，用示例文字把窗口渲染成 PNG（`QWidget.grab()` 可以直接画还没显示的窗口），用来调样式、给 README 配图；
- 设置环境变量 `SI_OVERLAY_SNAPSHOTS=<目录>` 后，真实运行时每 10 秒存一张窗口截图。用它确认了“后台线程 → 信号 → 界面刷新”这条链路在真实运行中是通的；
- `tests/test_overlay.py`：offscreen 平台下测 HTML 转义、只保留最近几句、字号上下限、鼠标穿透开关，CI 上也能跑。

**主要文件**：`simul_interp/ui/overlay.py`、`scripts/overlay_preview.py`、`tests/test_overlay.py`、`simul_interp/pipeline.py`（新增状态回调）、`simul_interp/asr/runner.py`

**验证**：pytest 共 33 个通过；预览图和真实运行截图显示正常（fr_meeting + 模拟翻译完整跑完并自动退出）。拖动、右键菜单、菜单栏图标、浮在全屏应用上这几项需要实际操作，还要用户在自己的屏幕上确认。

**经验**：界面代码也可以测。把“渲染出什么内容”写成返回 HTML 字符串的纯函数，就能在没有屏幕的环境里断言；真实的视觉效果再用截图确认。

## S8 · Windows 支持（2026-09-30）

**问题**：要在 Windows 上也能用，但开发机是 Mac，**没法在 Windows 真机上运行**。

**做法**
- **录音** `WindowsLoopbackSource`：用 PyAudioWPatch 调 WASAPI loopback，录默认扬声器声音的副本（不需要虚拟声卡，也不影响听原声）；设备原始格式通常是 48 kHz 双声道，混成单声道后用 soxr 流式重采样到 16 kHz。
- **识别** `FasterWhisperBackend`：faster-whisper（CTranslate2），同一个 large-v3 模型的另一种格式，有 NVIDIA 显卡时用 CUDA。参数和 MLX 后端保持一致：贪心解码（默认的 `beam_size=5` 慢得多）、只用一个温度（默认会用 6 个温度重试）、限制生成 token 数。默认 `local_files_only=True` 不自动下载，要在配置里 `allow_download = true`。
- 两个后端共用的“幻觉过滤”“合并被拆开的法语省音”提取到 `asr/common.py`。
- 界面菜单新增“重新连接音频设备”：Windows 切换耳机后需要手动点；macOS 也支持（重启录音小程序），但它本来就会自动重连。

**Windows 特有的两个坑（查文档和源码时发现的）**
1. **WASAPI loopback 在没有声音播放时根本不回调**。如果不处理，语音检测永远等不到“静音”，最后一句话就一直不会结束，也不会送去翻译。解决：`GapFiller` 记录最后一次收到音频的时刻，超过 0.1 秒没有新数据，就按时间补静音。（macOS 的 Core Audio Tap 没有声音时会持续给全零，没有这个问题。）
2. **PortAudio 只在初始化时枚举一次设备**，录音流开着的时候发现不了默认输出设备的变化。要自动跟随，需要另外调用 Windows 的 COM 接口，而这部分完全没法测试，所以这一版改成菜单里手动“重新连接”。

**没有 Windows 真机，怎么尽量降低风险**
- 读 PyAudioWPatch 的示例和源码、faster-whisper 的函数签名，确认接口和异常类型，不凭记忆写；
- 把 Windows 特有的逻辑拆成纯函数（`GapFiller`）单独测试；faster-whisper 后端用一个假的 `faster_whisper` 模块测参数和结果转换；
- 新增 GitHub Actions：每次推送都在 Linux、Windows、macOS 上跑单元测试；在 Windows 上**按 README 完整安装一遍依赖**，检查 Windows 专用模块能否导入、语音检测模型能否加载、命令行能否启动。
- 另外处理了 Windows 控制台的两个小问题：输出重定向时编码可能不是 UTF-8（打印中文会报错）；旧版控制台默认不解析 ANSI 颜色码。

**主要文件**：`simul_interp/audio/windows_loopback.py`、`simul_interp/asr/faster_whisper_backend.py`、`simul_interp/asr/common.py`、`.github/workflows/tests.yml`、`tests/test_windows.py`

**验证**：新增 3 个测试，pytest 共 36 个通过。真实的 Windows 录音和识别还需要在 Windows 电脑上实际跑一次。

**经验**：跨平台代码，“能在目标平台上安装和导入”是最低保证，CI 可以很便宜地做到；而“真的能录到声音、识别够快”必须在真机上验证。在 README 里明确写出哪些部分还没验证过。

## S9a · 延迟优化：测量、停顿时提前识别、量化选项（2026-09-30）

**问题**：要“延迟尽可能低”，得先知道时间花在哪里、哪些改动真的有用。

**1. 先测时间花在哪**：识别一次约 756 ms，其中编码器 306 ms（40%），解码器约 450 ms（60%），每生成一个 token 约 21 ms。
- “只编码实际长度（不补齐到 30 秒）”最多省 25%，却偏离模型训练条件，**不做**。
- 解码器才是瓶颈：large-v3 的解码器有 32 层，每生成一个 token 都要把约 1.8 GB 权重读一遍。

**2. 在内存里量化权重（`asr.quantize_bits`，默认关闭）**：还是同一个 large-v3，不下载任何东西，用 `mlx.nn.quantize` 把权重量化成 8 位或 4 位，再放进 mlx_whisper 的模型缓存（`ModelHolder`）。
- 三段测试音频：原始 876 ms → 8 位 745 ms（-15%）→ 4 位 656 ms（-25%），识别文字完全一致。
- 数值精度略有变化，而用户规定只用“完整版”模型，所以**默认关闭，等用户决定**。

**3. 停顿时提前识别**：VAD 在静音持续 128 ms 时发出 `pause` 事件，识别不等固定间隔、马上跑一次。如果真是说完了，等 VAD 在 400 ms 时判定结束，这次结果已经覆盖整句，可以直接确认。

**4. 新的幻觉路径，以及更好的修法**：停顿触发的那次识别，有时是对着“整句确认、在句末切过之后”只剩静音的缓冲区跑的，又幻觉出 “chaîne.”，说完时被当成“上一次识别已覆盖”直接确认了。
- 根本原因：识别模块只拿到声音，不知道哪段是真的有人在说话，而 VAD 其实知道。
- 修法：VAD 给每块音频标上“是否在说话”，识别模块记下缓冲区里（切过之后）的说话到哪儿为止。没有新的说话就不识别；说完时如果缓冲区里的说话不到 0.3 秒，就不确认任何尾巴。
- 第一版回归测试**没有复现问题**（缓冲区不到 0.5 秒，本来就不会识别）。改成贴近真实时序后，确认“去掉修复会失败、加上修复会通过”。

**5. 工具**：`--set 段.项=值` 临时覆盖配置，做对比实验不用改文件；`bench-asr` 开头打印配置，结尾统计“识别占用”（识别耗时占音频时长的比例，越高芯片越热）。

**实验数据**（fr_meeting，同一台 M5 MacBook Air，前后连续测）

| 配置 | 单次识别 | 识别占用 | 句末延迟（中位数 / 90%） | 闪烁的错字 |
|---|---|---|---|---|
| A 原始精度，间隔 0.6 s | 0.73 s | 98% | 1.79 / 2.56 s | 28% |
| B 4 位量化，间隔 0.6 s | 0.62 s | 92% | **1.11** / 2.16 s | 26% |
| B2 同 B（修复后重测） | 0.72 s | 96% | 1.46 / 2.49 s | 22% |
| C 4 位量化，间隔 1.0 s | 0.61 s | 63% | 1.21 / 2.00 s | 15% |
| D 原始精度，间隔 1.0 s | 0.92 s | 87% | 1.71 / 3.26 s | 16% |

一直说话的 fr_continuous 上，间隔 1.0 s 反而明显变差（句末延迟 3.8~4.4 s，间隔 0.6 s 时约 2.3~2.7 s）：识别少了，“两次一致”的确认就慢，缓冲区没法及时切短，每次要解码的内容更多，形成恶性循环。**所以默认间隔保持 0.6 s。**

**这台电脑的限制**：无风扇的 MacBook Air 连续满负荷识别后会降频。同一段 5 秒音频，开工时 750~830 ms，连续测了十几轮后 850~900 ms；同一配置（B 和 B2）前后两次的句末延迟相差 0.35 s。**比较配置时要注意测量顺序和芯片温度**；长时间开会时，large-v3 一直满载，延迟会随发热变大。

**主要文件**：`simul_interp/vad.py`、`simul_interp/asr/runner.py`、`simul_interp/asr/streaming.py`、`simul_interp/asr/mlx_backend.py`、`simul_interp/config.py`、`simul_interp/__main__.py`、`simul_interp/bench.py`、`tests/`

**验证**：pytest 共 39 个通过（新增停顿事件、`--set`、“切过后只剩静音不识别也不确认”的回归测试）；修复后 4 位量化重跑，结尾不再出现幻觉。

**经验**
- 优化前先拆解耗时，否则容易在不是瓶颈的地方（编码器）花力气。
- 参数之间会相互影响：“识别间隔”看起来只影响刷新频率，实际上还影响确认速度、缓冲区长度，进而影响每次识别的耗时。
- 在会降频的笔记本上做性能对比，测量本身就会被前一次测量影响，结论要留余量，最好交替测、多测几次。
