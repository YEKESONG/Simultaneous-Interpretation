## S0 · 项目骨架与开发规范（2026-09-30）

**问题**：从空仓库开始，要先定好目录结构、依赖、配置方式和提交规范，后面每个阶段才能往里填。

**做法**
- 目录采用“平铺包”结构：`simul_interp/` 直接放在仓库根目录，不装包也能用 `python -m simul_interp` 运行，对初学者最直观。
- 配置分三层：代码默认值 → `config.toml` → 命令行参数。写错配置项名会直接报错，避免拼错了却悄悄不生效。
- API 密钥只放在 `.env` 或环境变量里，`config.toml`、`.env`、音频文件、会话记录都写进 `.gitignore`，防止把密钥和隐私内容推到 GitHub。
- 依赖用 `requirements.txt` 的平台标记（`; sys_platform == "darwin"`）区分 macOS 和 Windows，一份文件两边通用。
- 本机开发环境：用 `ml` conda 环境的 Python 建 `.venv --system-site-packages`，复用已装好的 torch / mlx-whisper，只把新依赖装进项目自己的环境，不污染 `ml`。

**主要文件**：`simul_interp/config.py`、`simul_interp/__main__.py`、`config.example.toml`、`.env.example`、`requirements.txt`、`.gitignore`、`CLAUDE.md`

**验证**：`python -m pytest` 通过配置相关的 4 个测试；`python -m simul_interp config` 能打印生效配置。

**开工前的测量**：完整版 whisper-large-v3（MLX）在 M5 上识别一次约 0.83～0.93 秒，基本与音频长短无关（Whisper 总是把输入补齐到 30 秒）；打开逐词时间戳会再多约 0.4 秒。所以后面的流式识别不用逐词时间戳，改用 Whisper 自带的分段时间戳。

**经验**：先做一次粗测再设计。这 1 秒的固定开销直接决定了“每隔多久识别一次”和整体能做到多低的延迟。

## S1 · macOS 内录系统声音（2026-09-30）

**问题**：要录到“电脑正在播放的声音”（会议软件、浏览器），同时不能影响用户用耳机或扬声器听原声，也不想让用户装虚拟声卡。

**做法**
- 自己写了一个约 250 行的 Swift 小程序 `native/macos/si_audio_tap.swift`，用 macOS 14.2+ 的 Core Audio Taps：
  1. `CATapDescription(monoGlobalTapButExcludeProcesses: [])`：把所有进程的声音混成一路单声道；
  2. `muteBehavior = .unmuted`：只复制不静音，原声照常播放（这就是不需要“多输出设备”的原因）；
  3. tap 不能直接读，要挂到一个**只包含这个 tap** 的私有聚合设备上，再注册 IOProc 回调取数据；
  4. 用 `AVAudioConverter` 从 48 kHz 重采样到 16 kHz，以 float32 写到 stdout；日志用 JSON 写到 stderr。
- 没有直接用 audiotee：它没有声明开源许可证，不能放进仓库；读它的代码学用法，自己实现更可控。
- 默认输出设备变化（插拔耳机、连蓝牙）时，小程序以退出码 3 退出，Python 端立刻重启它，重新挂到新设备上。
- Python 端 `simul_interp/audio/`：统一的 `AudioSource` 基类把任意长度的数据切成 512 点（32 ms）的小块并打上“音频流时间”；`record` 命令用来检查内录。

**踩坑：没权限时系统不报错，只给静音**
- 第一次测试收到的数据量完全正常（每秒 16000 个采样点），但全部是 0。
- 原因：macOS 把“系统录音”权限记在**负责进程**头上，也就是启动它的应用。当时是 Claude 应用在后台启动它，Claude 没有申请这项权限，所以既不弹窗也拿不到声音。
- 解决：小程序启动后用 `responsibility_spawnattrs_setdisclaim` 重新启动自己，声明“我自己负责”，同时把带 `NSAudioCaptureUsageDescription` 的 Info.plist 用 `-sectcreate` 嵌进可执行文件。之后系统以 si-audio-tap 的名义弹出权限框，从终端、VS Code 还是别的应用启动都一样。
- 排查方法：程序卡住时用 `sample <pid>` 看调用栈，发现停在创建 tap 的调用里、并且加载了 TCC（权限）框架，从而确认是在等权限弹窗。
- 重新编译会让 macOS 把它当成新程序、可能再要一次权限，所以 Python 端按**源码哈希**决定是否重新编译，而不是按修改时间。

**主要文件**：`native/macos/si_audio_tap.swift`、`native/macos/Info.plist`、`scripts/build_macos_tap.sh`、`simul_interp/audio/base.py`、`simul_interp/audio/macos_tap.py`、`simul_interp/audio/util.py`

**验证**
- 播放一段 6.9 秒的法语合成语音同时内录：音量 -14～-16 dBFS，播完后是真正的全零静音；
- 把录到的音频交给 Whisper，识别结果与原文一字不差；
- `python -m simul_interp record --seconds 9` 正常出音量条并保存 WAV；pytest 6 个测试通过。

**经验**：系统级功能先写一个最小可运行的探针，用“数据量对不对、是不是全零、内容对不对”三步验证，比一上来就接进完整流程好排查得多。

## S2 · 音频文件模拟源与测试音频（2026-09-30）

**问题**：调识别和翻译时不可能每次都开一个真实会议；用户的真实录音又涉及隐私，不能放进仓库，也不适合反复发给翻译 API。

**做法**
- `FileAudioSource`：用 ffmpeg 把任意格式解码成 16 kHz 单声道，**按真实语速**一块一块送出。每一块都等到它“播放完”的时刻才送，和真实内录一样（声音总是播完才拿得到），所以用它测出来的延迟就是真实延迟。
- 文件结束后补 1.5 秒静音，让语音检测能判断最后一句已经说完。
- `speed=0` 表示不等待、尽快送完，只用于离线单元测试。
- `scripts/make_test_audio.py`：用 macOS 自带的法语语音 Thomas 合成两段内容相同、节奏不同的测试音频，并附带逐句的标准答案：
  - `fr_meeting.wav`（62 秒）：句间停顿 0.7 秒，模拟正常发言；
  - `fr_continuous.wav`（51 秒）：几乎不停顿、语速更快，模拟“一直有人在说话”的最难情况。
- 生成的音频放在 `samples/`，已被 `.gitignore` 忽略，需要时运行脚本重新生成即可。

**主要文件**：`simul_interp/audio/file_source.py`、`scripts/make_test_audio.py`、`tests/test_file_source.py`

**验证**：新增 2 个测试，一个检查切块和补静音，一个检查按实时速度送出（0.5 秒音频约 0.5 秒送完，且每块都在播放完之后才送）；pytest 共 8 个通过。

**经验**：测试数据要“可重复、无隐私、有标准答案”。合成语音不如真人录音难，但足够用来调流程和测延迟；准确率最终还要用真实录音在本地检验。

## S3 · 语音检测与分段（2026-09-30）

**问题**：Whisper 不能一直对着所有声音跑：没人说话时浪费算力，还容易在静音上“幻觉”出不存在的句子（比如凭空出现“谢谢观看”）。同时需要尽快知道“一句话说完了”，这是降低延迟的关键。

**做法**
- 用 Silero VAD（随 pip 包附带的约 2 MB 小模型，只判断有没有人声，不做转写），每 32 毫秒给出一个说话概率。
- 判断逻辑写成与模型无关的状态机 `VadSegmenter`，输出“开始 / 音频 / 结束”三种事件：
  - **迟滞双阈值**：概率 ≥ 0.5 才算开始说话，说话中低于 0.35 才开始计静音，避免在阈值附近反复开关；
  - **静音 400 毫秒**判定一句结束（向上取整成 13 块，保证至少 400 毫秒）；
  - **句首预留 200 毫秒**：开始说话前的几块也一起送给识别，避免吞掉第一个音；
  - 说话中的静音块照样送给识别，因为词尾常常落在这些块里。
- `vad` 命令：只跑语音检测并打印每段起止时间，用来调参数。
- 全局 `--file / --speed` 参数：任何命令都可以改用音频文件作为输入。

**主要文件**：`simul_interp/vad.py`、`tests/test_vad.py`、`simul_interp/__main__.py`

**验证**
- 4 个状态机测试（预留与结束时机、短停顿不切句、迟滞、收尾），pytest 共 12 个通过；
- `fr_meeting.wav` 正好切出 10 段，与 10 句话一一对应；
- `fr_continuous.wav` 整段 51 秒被当成一段（没有超过 400 毫秒的停顿），说明后面的流式识别**不能只靠停顿来定稿**；
- 每块检测耗时 0.11 毫秒，可以忽略。

**经验**：把“模型”和“判断逻辑”拆开。逻辑部分用构造的概率序列就能精确测试；另外注意 Python 的 `round(12.5) == 12`（四舍六入五成双），涉及“至少多长”时用 `math.ceil`。

## S4 · Whisper 流式识别（2026-09-30）

**问题**：Whisper 一次只能处理一整段音频，本身不会“边听边出字”；而且识别一次固定要约 0.8 秒，只看一次结果也不可靠（截在词中间的 3 秒音频曾被识别成 “l'électro-électriq”）。

**做法：LocalAgreement（参考 ufal/whisper_streaming 的思路，按本项目需要重写）**
- 说话期间每隔约 0.6 秒，把缓冲区（这句话到目前为止的音频）整段重新识别一次；
- **本次和上一次开头一致的部分才“确认”**，确认后不再改，可以送去翻译；不一致的尾巴是“暂定”，只用来灰字显示；
- 已确认的词**只追加、不替换**：Whisper 偶尔会把已确认的词换个写法甚至漏掉，用编辑距离把新结果和已确认部分对齐，而不是要求逐字相同，这样既不会重复发出，也不会丢词；
- **切缓冲区**：一整句确认完（Whisper 分段以句号、问号结尾）就切掉这段音频，已确认的文字作为提示词带给下一次，缓冲区一直很短、每次识别都快；
- **VAD 判定说完时**：如果上一次识别已经覆盖到说话结束，直接确认剩下的尾巴，省一次识别（约 0.8 秒）；
- 模型只从本地缓存加载（传本地路径给 mlx_whisper），找不到就报错，不会自动下载。

**用数据驱动的三次改进**（新增 `bench-asr` 命令：按真实语速跑测试音频，用一次离线的逐词时间戳识别作参照，统计每个词的显示延迟和确认延迟）
1. 长句没有句号时缓冲区越积越长，单次识别从 0.7 秒涨到 1.4 秒，还出现过一次 3.3 秒的强制切分。
   → 缓冲区超过 6 秒时，识别顺带输出逐词时间戳，直接切在已确认的逗号或词后面。
2. 音频很短时 Whisper 会“编下去”，把提示词里的上一句接着复述一遍（灰字里闪过错字）。
   → 加语速上限（每秒最多 6 个词，超出就截掉）；一句话开头、音频不到 1.5 秒时先不给提示词。
3. 逐词时间戳会把法语的省音和连字符拆开（d'être → “d” + “'être”，Est-ce → “Est” + “-ce”），导致前后两次结果对不上，确认被拖慢。
   → 没有前导空格的片段并回前一个词，与 `text.split()` 的分词保持一致。

**结果**（M5，完整版 large-v3，两段 60 秒左右的法语合成语音）

| 指标 | fr_meeting（句间有停顿） | fr_continuous（几乎不停顿） |
|---|---|---|
| 显示延迟（中位数 / 90%） | 0.98 / 1.64 秒 | 1.31 / 2.05 秒 |
| 确认延迟（中位数 / 90%） | 1.75 / 2.62 秒 | 2.30 / 3.09 秒 |
| 句末延迟（中位数） | 1.70 秒 | 2.46 秒 |
| 单次识别平均 / 最慢 | 0.73 / 1.57 秒 | 0.93 / 1.56 秒 |
| 暂定文字里的错词 | 25%（改进前 29%） | 16%（改进前 19%） |
| 词错误率 WER | 5.6% | 5.6% |

WER 里剩下的主要是数字写法（douze → 12、sept pour cent → 7%），意思没有错；确认下来的全文没有重复、没有丢词。

**主要文件**：`simul_interp/asr/streaming.py`、`simul_interp/asr/mlx_backend.py`、`simul_interp/asr/runner.py`、`simul_interp/bench.py`、`tests/test_streaming.py`

**验证**：6 个流式识别测试用“假识别后端”按剧本返回结果，并故意把正说到一半的词截断，覆盖“两次一致才确认”、整段不重复不丢词、切缓冲区、复用上一次结果、无句号时强制切分；pytest 共 18 个通过。

**经验**
- 先把“怎么衡量”做出来（`bench-asr`），每次改动都用同一把尺子量，改进才有方向。第一版的问题（长句变慢、灰字幻觉、法语省音被拆开）都是看数据看出来的。
- MLX 的计算流按线程区分，模型的加载和每一次识别必须在同一个线程里，所以加载放在识别线程里做。

## S5 · 流式翻译（2026-09-30）

**问题**：确认下来的法语要尽快变成中文：既不能一个词一个词地翻（没有上下文、翻不准），也不能等整段说完再翻（太慢）。

**做法**
- `ChatTranslator`：调用任何兼容 OpenAI Chat Completions 的接口，直接用 httpx 解析 SSE 流（`data: {...}` 一行一条，`[DONE]` 结束），不依赖 openai SDK，也能看清流式接口到底是怎么回事。
- **什么时候送去翻译**（`UnitBuilder`，纯逻辑、可单测）：遇到句末标点就送；句子很长时，遇到逗号且已经攒够 8 个词，先送前半句；攒到 25 个词还没有标点也送；VAD 判定说完，剩下的全送。
- **上文**：带上前 3 句原文，放在用户消息里；系统提示词保持不变，固定的开头部分能被服务商缓存，更快也更便宜。
- **预热**：启动时先 `GET /models`，建立 TLS 连接并检查密钥，第一句话不用再花握手时间；密钥无效时在开始前就报错。
- **并发**：最多同时翻 3 段，一段慢了不会堵住后面的；翻译失败只影响那一句。
- `bench-translate` 命令：逐句实测首字延迟和整句完成时间，方便比较不同服务商和模型。

**踩坑：查文档，不要凭记忆**
- 原本按记忆写了 `deepseek-chat`，实际查 DeepSeek 官方文档发现，现在最快的模型叫 `deepseek-flash`；
- 更关键的是，文档写明**思考模式默认开启**（effort 默认 high）。不关的话，每句话都要先“想”一阵才开始输出，对同传是致命的延迟。所以默认配置显式发送 `"thinking": {"type": "disabled"}`，并有单元测试守着这一条。

**主要文件**：`simul_interp/translate.py`、`tests/test_translate.py`、`simul_interp/bench.py`、`simul_interp/config.py`、`config.example.toml`

**验证**：4 个翻译测试，用 `httpx.MockTransport` 模拟服务端，检查 SSE 解析、请求内容（模型、流式、关闭思考、术语表、上文）、HTTP 错误和后台并发翻译；pytest 共 22 个通过。真实 API 的延迟要等填好密钥后用 `bench-translate` 实测。

**经验**：用 `httpx.MockTransport` 这类“假服务端”测网络代码，不需要密钥、不花钱、结果稳定，还能精确检查发出去的请求内容。

## S6 · 串起完整流程（终端版）与会话记录（2026-09-30）

**问题**：前面各阶段都是单独跑通的零件，要串成一个真正能用的程序：音频 → 语音检测 → 流式识别 → 翻译 → 显示，还要把结果存下来。

**做法**
- `Interpreter` 流水线只依赖一个很小的界面接口 `View`（`on_live` 显示正在说的话，`on_unit` 显示原文和流式译文），终端版和下一阶段的悬浮窗共用同一条流水线。
- 终端界面：每段原文、译文各打一行，并标出翻译的首字延迟和完成时间；最底下一行实时刷新“正在说的话”，灰色是还没确认的部分。
- 会话记录：每翻完一句就追加写入 Markdown，程序中途退出也不丢；几段译文并发进行、完成顺序不定，所以按原文顺序缓冲后再写。用文件做输入时命名为 `<文件名>_译文.md`，内录时命名为 `同传_<日期>_<时间>_译文.md`，已存在就不覆盖。本机配置把记录目录设为 `~/录音文件/录音译文`。
- `run` 命令：`--mock-translate` 用模拟翻译（不联网），没有密钥也能测试整条流程；没有密钥时只显示原文，不会报错退出。

**踩坑：确认下来的文字里混进了幻觉 “Merci.”**
- 第一次完整运行时，第 2、3 句之间多出一句原文没有的 “Merci.”，而且被确认、送去了翻译。
- 原因：VAD 判定说完后要再识别一次，而缓冲区末尾带着约 0.4 秒静音，Whisper 对着静音“补”了一句（典型幻觉）。这次识别不经过“两次一致”的检验，所以直接被确认了。
- 修复：最后一次识别前，把缓冲区截到停止说话后 0.2 秒。顺带发现“太短不识别”原本按缓冲区长度判断，而缓冲区包含句首预留和句尾静音，这个判断永远不会生效，改为按实际说话时长判断（阈值 0.45 秒，含 0.2 秒预留，避免误丢 “Oui.” 这类短回答）。
- 新增两个回归测试：假识别后端在句尾静音超过 0.3 秒时会“补”一句 Merci.；修复前测试失败，修复后通过。

**主要文件**：`simul_interp/pipeline.py`、`simul_interp/ui/console.py`、`simul_interp/transcript.py`、`simul_interp/asr/streaming.py`、`tests/test_transcript.py`、`tests/test_streaming.py`

**验证**：pytest 共 26 个通过；用 fr_meeting 和模拟翻译完整跑一遍，13 段原文完整、顺序正确、没有幻觉，长句在逗号处拆成两段，会话记录按顺序写好。

**经验**：单独测零件发现不了的问题（比如这个只在“说完后再识别一次”时出现的幻觉），要靠端到端跑一遍才能暴露。发现 bug 先写一个能复现它的测试，再修。

## S7a · 修复实测中发现的三个识别问题（2026-09-30）

**问题**：做悬浮窗时真实跑了几遍完整流程，又暴露出三个只在特定时机才出现的识别问题（每次运行的线程调度和识别时机都不完全一样，所以前几次没遇到）。

**1. 切在词中间，下一段开头的半个词被识别成别的词**
- 现象：确认的文字里出现了原文没有的 “heures.”。
- 原因：长句的缓冲区超过 6 秒后按 Whisper 的逐词时间戳切，而时间戳有 0.1~0.3 秒误差，切点落在了 “utilisateurs” 中间，下一段开头只剩 “-teurs” 的尾音。
- 修复：不完全相信时间戳，在切点前后 0.25 秒内找声音最小的 20 毫秒切下去；一样安静时取离原切点最近的。词与词之间的真实停顿比模型估的时间戳可靠。

**2. Whisper 陷入重复循环，一次识别花了 4.65 秒**
- 现象：识别结果是 “…de la version de la version de la version de…”，解码一直生成到默认上限 224 个 token。
- 修复：按音频长度限制最多生成的 token 数（每秒 10 个，正常语速不到 5 个），解码时间有了上限；再检测“同一个 2~4 词短语连续出现 3 次以上”，只保留第一次（单个词要连续 4 次才算，“non non non” 可能是真的）。

**3. 结尾对着静音“补”出一句（“Merci.”、“chaîne.”）**
- 原因：最后一句已经被“两次一致”确认完，但 VAD 判定说完后又对剩下的音频识别了一次，而剩下的几乎全是静音。这次识别不经过两次一致的检验，幻觉就直接被确认了。
- 第一次修复只判断了“切过缓冲区后剩下的说话不到 0.3 秒”，但句尾正好落在缓冲区末尾时切不开，又漏出一个 “chaîne.”。
- 最终判断标准：**上一次识别之后，还有没有新说的话**。上一次听到的内容都已确认、之后又说了不到 0.3 秒，就不再识别；需要识别时，只保留停止说话后 0.1 秒。

**主要文件**：`simul_interp/asr/streaming.py`、`simul_interp/asr/mlx_backend.py`、`simul_interp/asr/types.py`、`tests/test_streaming.py`

**验证**
- 新增 3 个测试：切点挪到真实停顿里、重复循环截断、“整句确认后只剩静音时不再识别”（假后端会对纯静音补一句 Merci.；临时关掉修复时这个测试失败，打开后通过）；pytest 共 29 个通过。
- 两段测试音频重跑：确认下来的全文完整、没有碎片词、结尾没有幻觉，最慢一次识别从 4.65 秒降到 2.1 秒以内。

**注意：延迟有波动**。同样的代码连续跑，fr_continuous 的确认延迟中位数在 2.2~2.7 秒之间变化。这台是无风扇的 MacBook Air，连续十几轮满负荷识别后可能发热降频（未专门验证）。长时间开会时要留意这一点。

**经验**
- 写回归测试时，先确认“去掉修复后测试会失败”，否则测试可能根本没复现问题。这次第一版测试就没复现：它喂了实际中不会出现的长静音。
- 修复要找到真正的判断标准。“切过缓冲区”只是表面条件，“上一次识别之后有没有新说的话”才是本质。

## S7b · 透明悬浮字幕窗（2026-09-30）

**问题**：开会或看视频时，字幕要浮在画面上：看得清、不挡操作、不抢焦点，全屏时也要能看到。

**做法（PySide6）**
- 外观：半透明深色圆角背景；上面一行法语原文（小字、浅灰），下面一行中文译文（大字、白色），正在流式输出的译文末尾有灰色 “…”；最底下是正在说的话，白色是已确认的、灰色是暂定的。文字加阴影，背景调得很透明时压在亮色画面上也看得清。
- 窗口：无边框、始终置顶、不接受焦点（在会议软件里打字不会被打断），显示时也不激活。
- **macOS 全屏**：Qt 没有提供“出现在所有桌面空间、浮在全屏应用上面”的设置。这里用 ctypes 直接给 NSWindow 发 Objective-C 消息（`setCollectionBehavior:`、`setLevel:`、`setHidesOnDeactivate:`），并把程序设为“辅助应用”（不在程序坞显示），不需要额外安装 PyObjC。
- 操作：拖动移动，右下角调整大小；右键菜单调字号、背景深浅、鼠标穿透、清空、退出。开启穿透后窗口本身收不到点击，所以同样的菜单也放在菜单栏图标里，用来解锁和退出。
- 位置、大小、字号、背景透明度退出时用 QSettings 保存，下次启动自动恢复。
- 线程：识别和翻译在后台线程里跑，结果以不可变的快照通过 Qt 信号交给界面线程，每 50 毫秒最多刷新一次。
- 用文件做输入时，放完 5 秒自动退出；内录要用户自己退出。

**踩坑**
- **macOS 上不能用 Qt 的 Tool 窗口类型**：它会在切换到别的应用时自动隐藏，而我们恰恰需要在别的应用处于前台时显示。Windows 上用 Tool 类型，是为了不在任务栏占位置。
- **Qt 事件循环里 Python 收不到 Ctrl+C**：事件循环在 C++ 里跑，用一个每 200 毫秒触发一次的空定时器让解释器有机会处理信号。
- **offscreen 模式下调用原生接口会段错误**：单元测试用 Qt 的 offscreen 平台，这时窗口句柄不是 NSView，对它发 Objective-C 消息会直接崩溃。改为只在 Qt 平台是 cocoa 时调用。
- **Retina 屏截图是 2 倍像素**：预览脚本拼背景图时要按 `devicePixelRatio` 换算，否则比例不对。

**看不到屏幕，怎么验证界面**
- `scripts/overlay_preview.py`：不跑识别，用示例文字把窗口渲染成 PNG（`QWidget.grab()` 可以直接画还没显示的窗口），用来调样式、给 README 配图；
- 设置环境变量 `SI_OVERLAY_SNAPSHOTS=<目录>` 后，真实运行时每 10 秒存一张窗口截图。用它确认了“后台线程 → 信号 → 界面刷新”这条链路在真实运行中是通的；
- `tests/test_overlay.py`：offscreen 平台下测 HTML 转义、只保留最近几句、字号上下限、鼠标穿透开关，CI 上也能跑。

**主要文件**：`simul_interp/ui/overlay.py`、`scripts/overlay_preview.py`、`tests/test_overlay.py`、`simul_interp/pipeline.py`（新增状态回调）、`simul_interp/asr/runner.py`

**验证**：pytest 共 33 个通过；预览图和真实运行截图显示正常（fr_meeting + 模拟翻译完整跑完并自动退出）。拖动、右键菜单、菜单栏图标、浮在全屏应用上这几项需要实际操作，还要用户在自己的屏幕上确认。

**经验**：界面代码也可以测。把“渲染出什么内容”写成返回 HTML 字符串的纯函数，就能在没有屏幕的环境里断言；真实的视觉效果再用截图确认。

## S8 · Windows 支持（2026-09-30）

**问题**：要在 Windows 上也能用，但开发机是 Mac，**没法在 Windows 真机上运行**。

**做法**
- **录音** `WindowsLoopbackSource`：用 PyAudioWPatch 调 WASAPI loopback，录默认扬声器声音的副本（不需要虚拟声卡，也不影响听原声）；设备原始格式通常是 48 kHz 双声道，混成单声道后用 soxr 流式重采样到 16 kHz。
- **识别** `FasterWhisperBackend`：faster-whisper（CTranslate2），同一个 large-v3 模型的另一种格式，有 NVIDIA 显卡时用 CUDA。参数和 MLX 后端保持一致：贪心解码（默认的 `beam_size=5` 慢得多）、只用一个温度（默认会用 6 个温度重试）、限制生成 token 数。默认 `local_files_only=True` 不自动下载，要在配置里 `allow_download = true`。
- 两个后端共用的“幻觉过滤”“合并被拆开的法语省音”提取到 `asr/common.py`。
- 界面菜单新增“重新连接音频设备”：Windows 切换耳机后需要手动点；macOS 也支持（重启录音小程序），但它本来就会自动重连。

**Windows 特有的两个坑（查文档和源码时发现的）**
1. **WASAPI loopback 在没有声音播放时根本不回调**。如果不处理，语音检测永远等不到“静音”，最后一句话就一直不会结束，也不会送去翻译。解决：`GapFiller` 记录最后一次收到音频的时刻，超过 0.1 秒没有新数据，就按时间补静音。（macOS 的 Core Audio Tap 没有声音时会持续给全零，没有这个问题。）
2. **PortAudio 只在初始化时枚举一次设备**，录音流开着的时候发现不了默认输出设备的变化。要自动跟随，需要另外调用 Windows 的 COM 接口，而这部分完全没法测试，所以这一版改成菜单里手动“重新连接”。

**没有 Windows 真机，怎么尽量降低风险**
- 读 PyAudioWPatch 的示例和源码、faster-whisper 的函数签名，确认接口和异常类型，不凭记忆写；
- 把 Windows 特有的逻辑拆成纯函数（`GapFiller`）单独测试；faster-whisper 后端用一个假的 `faster_whisper` 模块测参数和结果转换；
- 新增 GitHub Actions：每次推送都在 Linux、Windows、macOS 上跑单元测试；在 Windows 上**按 README 完整安装一遍依赖**，检查 Windows 专用模块能否导入、语音检测模型能否加载、命令行能否启动。
- 另外处理了 Windows 控制台的两个小问题：输出重定向时编码可能不是 UTF-8（打印中文会报错）；旧版控制台默认不解析 ANSI 颜色码。

**主要文件**：`simul_interp/audio/windows_loopback.py`、`simul_interp/asr/faster_whisper_backend.py`、`simul_interp/asr/common.py`、`.github/workflows/tests.yml`、`tests/test_windows.py`

**验证**：新增 3 个测试，pytest 共 36 个通过。真实的 Windows 录音和识别还需要在 Windows 电脑上实际跑一次。

**经验**：跨平台代码，“能在目标平台上安装和导入”是最低保证，CI 可以很便宜地做到；而“真的能录到声音、识别够快”必须在真机上验证。在 README 里明确写出哪些部分还没验证过。

## S9a · 延迟优化：测量、停顿时提前识别、量化选项（2026-09-30）

**问题**：要“延迟尽可能低”，得先知道时间花在哪里、哪些改动真的有用。

**1. 先测时间花在哪**：识别一次约 756 ms，其中编码器 306 ms（40%），解码器约 450 ms（60%），每生成一个 token 约 21 ms。
- “只编码实际长度（不补齐到 30 秒）”最多省 25%，却偏离模型训练条件，**不做**。
- 解码器才是瓶颈：large-v3 的解码器有 32 层，每生成一个 token 都要把约 1.8 GB 权重读一遍。

**2. 在内存里量化权重（`asr.quantize_bits`，默认关闭）**：还是同一个 large-v3，不下载任何东西，用 `mlx.nn.quantize` 把权重量化成 8 位或 4 位，再放进 mlx_whisper 的模型缓存（`ModelHolder`）。
- 三段测试音频：原始 876 ms → 8 位 745 ms（-15%）→ 4 位 656 ms（-25%），识别文字完全一致。
- 数值精度略有变化，而用户规定只用“完整版”模型，所以**默认关闭，等用户决定**。

**3. 停顿时提前识别**：VAD 在静音持续 128 ms 时发出 `pause` 事件，识别不等固定间隔、马上跑一次。如果真是说完了，等 VAD 在 400 ms 时判定结束，这次结果已经覆盖整句，可以直接确认。

**4. 新的幻觉路径，以及更好的修法**：停顿触发的那次识别，有时是对着“整句确认、在句末切过之后”只剩静音的缓冲区跑的，又幻觉出 “chaîne.”，说完时被当成“上一次识别已覆盖”直接确认了。
- 根本原因：识别模块只拿到声音，不知道哪段是真的有人在说话，而 VAD 其实知道。
- 修法：VAD 给每块音频标上“是否在说话”，识别模块记下缓冲区里（切过之后）的说话到哪儿为止。没有新的说话就不识别；说完时如果缓冲区里的说话不到 0.3 秒，就不确认任何尾巴。
- 第一版回归测试**没有复现问题**（缓冲区不到 0.5 秒，本来就不会识别）。改成贴近真实时序后，确认“去掉修复会失败、加上修复会通过”。

**5. 工具**：`--set 段.项=值` 临时覆盖配置，做对比实验不用改文件；`bench-asr` 开头打印配置，结尾统计“识别占用”（识别耗时占音频时长的比例，越高芯片越热）。

**实验数据**（fr_meeting，同一台 M5 MacBook Air，前后连续测）

| 配置 | 单次识别 | 识别占用 | 句末延迟（中位数 / 90%） | 闪烁的错字 |
|---|---|---|---|---|
| A 原始精度，间隔 0.6 s | 0.73 s | 98% | 1.79 / 2.56 s | 28% |
| B 4 位量化，间隔 0.6 s | 0.62 s | 92% | **1.11** / 2.16 s | 26% |
| B2 同 B（修复后重测） | 0.72 s | 96% | 1.46 / 2.49 s | 22% |
| C 4 位量化，间隔 1.0 s | 0.61 s | 63% | 1.21 / 2.00 s | 15% |
| D 原始精度，间隔 1.0 s | 0.92 s | 87% | 1.71 / 3.26 s | 16% |

一直说话的 fr_continuous 上，间隔 1.0 s 反而明显变差（句末延迟 3.8~4.4 s，间隔 0.6 s 时约 2.3~2.7 s）：识别少了，“两次一致”的确认就慢，缓冲区没法及时切短，每次要解码的内容更多，形成恶性循环。**所以默认间隔保持 0.6 s。**

**这台电脑的限制**：无风扇的 MacBook Air 连续满负荷识别后会降频。同一段 5 秒音频，开工时 750~830 ms，连续测了十几轮后 850~900 ms；同一配置（B 和 B2）前后两次的句末延迟相差 0.35 s。**比较配置时要注意测量顺序和芯片温度**；长时间开会时，large-v3 一直满载，延迟会随发热变大。

**主要文件**：`simul_interp/vad.py`、`simul_interp/asr/runner.py`、`simul_interp/asr/streaming.py`、`simul_interp/asr/mlx_backend.py`、`simul_interp/config.py`、`simul_interp/__main__.py`、`simul_interp/bench.py`、`tests/`

**验证**：pytest 共 39 个通过（新增停顿事件、`--set`、“切过后只剩静音不识别也不确认”的回归测试）；修复后 4 位量化重跑，结尾不再出现幻觉。

**经验**
- 优化前先拆解耗时，否则容易在不是瓶颈的地方（编码器）花力气。
- 参数之间会相互影响：“识别间隔”看起来只影响刷新频率，实际上还影响确认速度、缓冲区长度，进而影响每次识别的耗时。
- 在会降频的笔记本上做性能对比，测量本身就会被前一次测量影响，结论要留余量，最好交替测、多测几次。

## S9b · 投机翻译（2026-09-30）

**问题**：翻译要等原文“两次一致”确认后才开始，而确认本身就比“第一次识别出来”晚一次识别的时间（约 0.6~0.9 秒）。对用户来说，真正的延迟是“一句话说完 → 屏幕上出现中文”。

**做法：投机翻译（先猜后改）**
- 每次识别后，在“已确认但还没送出的词 + 暂定尾巴”里，用**和正式确认完全相同的切分规则**找第一个翻译单元；如果它需要暂定的词才能凑成，就先把它送去翻译，译文用浅蓝色显示在“正在说”那一行下面。
- 正式确认时：文字和投机的一样（忽略大小写和标点）就直接采用这份译文，不再请求；不一样就作废投机的那份（正在进行的请求会被断开），按确认后的文字重新翻译。
- 采用、作废、流式更新都在同一把锁下做，避免译文写到一半被另一个线程读到；译文到底显示在“正在说”那一行还是正式单元上，也由这把锁保证不会两边都显示。
- 新增 `bench-pipeline`：整条流水线按真实语速跑，统计“这段话的最后一个词说完 → 原文确认 / 开始出现中文 / 中文译完”。

**结果**（fr_meeting，模拟翻译，首字固定约 0.3 秒）

| | 投机翻译关 | 投机翻译开 |
|---|---|---|
| 说完 → **开始出现中文**（中位数 / 90%） | 1.83 / 2.89 秒 | **0.97 / 1.55 秒** |
| 说完 → 中文译完（中位数） | 3.26 秒 | 2.18 秒 |
| 命中 | — | 16 段中 15 段 |
| 翻译请求数 | 16 | 47 |

**代价**：请求数约为正常的 3 倍。暂定文字每变一次（比如 “encouragés.” → “encourageants.”）就会发起一次新请求，旧请求在收到第一个字时断开。试过把“最多靠几个暂定词凑成一句”从 12 收紧到 5，请求数并没有减少（49 次），说明浪费来自句尾一两个词的反复变化，而不是“瞎猜长句”，所以默认保持 12。服务商有频率限制、或者在意费用时，可以用 `translate.speculative = false` 关掉。

**主要文件**：`simul_interp/translate.py`、`simul_interp/pipeline.py`、`simul_interp/ui/overlay.py`、`simul_interp/ui/console.py`、`simul_interp/bench.py`、`tests/test_translate.py`

**验证**：新增 3 个测试（命中时只请求一次、且中文在原文确认前就出现；未命中时作废并重翻；凑不成单元或暂定部分太长时不投机），pytest 共 42 个通过；预览图确认浅蓝色投机译文的显示效果。

**经验**：“先猜后改”是同传系统降低延迟的常用思路（重新翻译 re-translation）。关键是：猜错了能干净地撤回（作废、断开请求），猜对了不重复花钱；衡量它要看端到端的指标，而不是单个模块的指标。

## S10 · 真实内录的端到端验证与已知问题（2026-09-30）

**问题**：之前“内录系统声音”（S1）和“完整流程”（S6、S7，用文件模拟）是分开验证的，还没有真正用内录的声音跑过整条流程。

**做法**：用内录模式运行同传（终端界面、模拟翻译），同时用 `afplay` 播放 20 秒法语测试音频。

**结果**：整条链路是通的。内录 → 语音检测 → 流式识别 → 投机翻译，前 4 句都是“投机翻译命中”，法语原文还没完全确认，中文就提前 0.3~0.5 秒出现了。

**发现的问题**：`afplay -t 20` 在第 20 秒从句子中间截断了声音，最后一句被识别成 “le taux d'erreur est de 1,5%”（原文是 “est passé de douze à sept pour cent”）。声音突然停在半句话时，说完后的最后一次识别不经过“两次一致”的检验，Whisper 会对着半句话“补全”出错误的结尾。真实使用中，突然暂停视频也会遇到。

**顺带踩的坑**：在非交互的 shell 里用 `&` 启动的后台进程，SIGINT（Ctrl+C）默认被忽略，所以测试脚本里 `kill -INT` 停不下来，要用 SIGTERM。录音小程序在 Python 退出、管道关闭后会自己退出，没有残留进程。

**已知问题（写进了 README）**
1. 声音在半句话处突然停止时，最后半句可能被“补全”错。
2. 投机翻译使翻译请求数约为正常的 3 倍。
3. 无风扇的 Mac 连续使用 large-v3 会发热降频，长时间使用延迟会变大；4 位量化能减轻，但默认关闭（改变了“完整版”的数值精度，等用户决定）。
4. Windows 部分还没有在真机上运行过。
5. 真实翻译 API 的延迟还没有实测（需要在 `.env` 填密钥后跑 `bench-translate`、`bench-pipeline`）。

## S10b · 全程序统一用高精度时钟（2026-09-30）

**问题**：S9b 推送后 Windows 的 CI 失败：“投机译文在原文确认之前就出现”的测试里，两个时间戳完全相等（都是 221.328）。

**原因**：Python 3.12 及以前在 Windows 上 `time.monotonic()` 的精度只有 15.6 毫秒，两件相隔几毫秒的事落在同一个时钟周期里。S8 时同类问题只放宽了测试容差，是治标不治本：这个精度同样会让程序里所有的延迟统计在 Windows 上变粗。

**做法**
- 新建 `simul_interp/clock.py`，全程序只从这里取时间：`now = time.perf_counter`（在 Windows 上用 QueryPerformanceCounter，精度远高于 1 毫秒）。所有时间戳都要互相相减，所以必须来自同一个时钟，一次换干净。
- 测试里的计时也改用同一个时钟（原来测试用 `monotonic`、程序用 `perf_counter` 的话，两个时钟起点不同，相减没有意义），并把 S8 时放宽的容差改回 10 毫秒。
- 批量替换时踩了个小坑：`audio/base.py` 里原来有局部变量 `now = time.monotonic()`，替换后变成 `now = now()`，局部变量遮住了同名函数，一调用就报错，已改名为 `received`。

**验证**：pytest 42 个通过；用 7 秒的法语音频完整跑一遍流程（投机翻译命中，中文比原文确认提前 0.24 秒出现）。

**经验**：这次不用登录就拿到了 CI 的完整报错，靠的是 S8 加的“失败时把日志写成注释”。修 bug 要修根因：上一次只放宽了容差，同样的问题换个地方又冒出来了。

## S11a · VAD 滞后的尾巴不再当成新的说话（2026-09-30）

**问题**：用真实 API 跑端到端时，结尾的 “chaîne.” 幻觉又出现了，还被翻译成了“链条。”。

**原因**：S9a 已经加了“切开后的缓冲区里没有真的说话就不识别”，但判断用的是“最后一块说话离缓冲区开头多远”。而一句话说完后，Silero VAD 的说话概率要**滞后 0.1~0.3 秒**才降下去，切开后的缓冲区开头只有上一句的这点尾巴，却刚好超过了门槛（识别 0.1 秒、确认 0.3 秒），于是识别对着它幻觉出 “chaîne.” 并被确认。

**做法**：记录每一段被 VAD 标为“在说话”的时间，按**总时长**判断；只对切开之后的缓冲区把门槛提高到 0.4 秒（滞后的尾巴到不了这么长，真的开始说下一句又很快会超过）。没切开过的缓冲区保持原来的判断，不影响 “Oui.” 这样很短的回答。

**验证**：新增回归测试（VAD 滞后 0.35 秒），确认换回旧判断时失败、新判断通过；pytest 43 个通过。两段测试音频重跑，结尾都没有幻觉。

**经验**：模型给出的“是否在说话”不是瞬时的，有滞后。依赖它做判断时，要按它的真实行为设门槛，并用贴近真实时序的测试去验证。

## S12 · 实时识别改用 turbo（2026-10-01）

**问题**：S11 显示，连续说话时 large-v3（即使 4 位量化）识别占用接近 100%，这台无风扇的 MacBook Air 一发热就跟不上，延迟越积越大。用户同意下载 turbo（解码器从 32 层减到 4 层）试测后再决定。

**怎么比较：几种测量各有局限**
1. **离线整段识别 8 段真实会议录音**（约 9 分钟，只在本机，只看统计数字），以 large-v3 原始精度为参照：8 位量化差异 2.2%，4 位 14.5%，turbo 28.9%。
2. **但参照本身不可靠**：同一个 large-v3 原始精度，离线识别时带不带逐词时间戳，结果就相差 25.8%。长音频按 30 秒窗口分段识别，逐词时间戳会改变下一个窗口从哪里开始，差异一路累积；而这段真实会议录音本身就很难。
3. **按实际同传方式**（流式）识别一段 125 秒真实录音：四种配置和参照的差异都在 20~23% 之间，落在参照本身的不确定范围内，分不出高低；turbo 的确认延迟中位数 1.72 秒（large-v3 各配置 2.67~2.97 秒），芯片占用 78%（large-v3 92~93%）。
4. **合成语音**（有真正的标准答案）：turbo 的 WER 是 6.8% / 4.9%，large-v3 在 5.6%~6.2%，基本一样。
5. **速度**：发热会让测试结果取决于先后顺序，所以在同一个进程里交替调用几个模型。turbo 比 large-v3 4 位快 1.4~1.9 倍，没有预想的 2 倍以上，因为 turbo 的编码器仍是 32 层，省下的只是解码器。另外，连续满负荷约半小时后，所有模型都比凉的时候慢约 40%。

**最后靠人看**：把两段真实录音的三种识别结果并排给用户看（只在本机，不进仓库）。turbo 把 “le dernier slide”（最后一页幻灯片）识别对了，large-v3 两种精度都听成了 “salade”（沙拉）；统计里 turbo “多出”的那些词，其实是 large-v3 漏掉的一段连贯对话。

**决定**：用户决定实时同传改用 turbo（不量化，对 turbo 来说量化提速很小），音频文件转写仍然只用完整版 large-v3；用户的全局规则和项目 `CLAUDE.md` 同步更新。Windows 端 faster-whisper 也改用 `large-v3-turbo`。

**结果（新默认配置，芯片较凉时开始连续测）**

| | fr_meeting | fr_continuous |
|---|---|---|
| 识别占用 | 66% | 73%（large-v3 时 99%） |
| 句末延迟中位数 | 0.89 秒 | 0.91 秒 |
| WER | 6.2% | 5.6% |
| **说完 → 开始出现中文**（真实 DeepSeek API，中位数 / 90%） | **0.90 / 1.15 秒** | **0.99 / 1.18 秒** |
| 投机翻译命中 | 17/18 | 13/13 |

连续说话时延迟不再越积越大；两段结尾都没有幻觉。投机翻译请求数约为段数的 4~5 倍。

**踩坑**
- huggingface_hub 默认的 Xet 下载在这里卡住（权重文件一直 0 字节），设 `HF_HUB_DISABLE_XET=1` 改用普通 HTTP 后 2 分钟下完。
- 基准测试的计时参照原来按模型名缓存，换模型会用被测模型重新生成，尺子就变了；改为参照一旦生成就固定使用。
- 新增 `scripts/compare_models.py`：离线比较几种配置，只输出统计数字（替换 / 漏掉 / 多出的词数），不输出识别文字（测试音频可能是隐私录音）。

**经验**
- 没有标准答案时，“和参照的差异”不等于“错误率”。先测一下参照自己有多稳定，才知道差异有多大意义。
- 数字之外，要让懂内容的人看实际输出：这次“差异最大”的恰恰是 turbo 识别得更好的地方。
- 在会发热的机器上比较速度，要让被比较的对象处在同样的条件下（同一进程交替测）。

## S13 · 字幕窗改版：原文译文成对同步出现，不闪不跳（2026-10-01）

**问题（用户实际使用后的反馈）**：法语原文一小段一小段地冒出来，译文却迟迟不出来；原文一直闪烁、弹出又消失，字幕区域一直在跳动、忽大忽小，眼睛很难聚焦到新的译文，连读旧译文都受影响；中文和法语字号差得太多。

**原因**
- 闪烁：最底下“正在说的话”随每次识别（约 0.4 秒一次）刷新，灰色的暂定文字时有时无，浅蓝色的投机译文也会出现又消失；
- 跳动：所有文字放在一个底部对齐的标签里，“正在说”那一行一折行，上面所有内容就整体上移，一缩短又下移。

**关键观察**：用 turbo 之后确认本身已经很快，而且投机翻译命中率很高，**原文被确认的那一刻，译文通常已经翻好了**（S12 实测“原文确认”中位数 0.91 秒，“开始出现中文”0.90 秒）。所以可以只在一对译文准备好时，把原文和译文一起显示，几乎不增加延迟。

**做法**
- **只显示成对的内容**：一对的译文翻完了，原文和译文才一起出现。个别译文迟迟翻不完的，开始出字 1 秒后先显示已翻出的部分；一个字都没出来的，4 秒后先只显示原文。正在识别的暂定文字和投机译文不再显示。
- **按顺序、不插队**：前一对还没准备好时，后面的先等着，新内容总是出现在最下面，已显示的内容不会被插队打乱位置。
- **平滑滚动**：每一对排成一块，从下往上堆。内容变化时先让原来最新的那块停在原位，再用 0.2 秒平滑地滑到新位置，眼睛能跟住。
- **越旧越暗**：最新的一对最亮，越往上颜色越暗，眼睛自然落在最新的译文上。
- **窗口大小固定**：不再用布局管理器，而是自己计算字幕区的位置并自己绘制（`QTextDocument`），文字再多也不会改变窗口的最小尺寸。
- **字号**：中文 22（原来 26），法语 = 中文 × 0.82 ≈ 18（原来 16），可以用 `ui.source_font_ratio` 调整。样式改版后旧版保存的字号不再沿用（`STYLE_VERSION`），位置和大小保留。
- **右上角小圆点**：听到有人说话时变绿，表示它在工作，但不占用字幕的位置。

**怎么客观衡量“闪不闪、跳不跳”**：用旧版（从 Git 取出，放在临时目录）和新版分别跑一遍 fr_meeting（真实翻译 API），每 0.2 秒截一张字幕窗的图，逐帧对比：

| | 旧版 | 新版 |
|---|---|---|
| 画面有变化的帧 | 36% | **12%** |
| 变化事件 | 每分钟 80 次 | **每分钟 19 次**（-76%） |
| 上半部分（正在读的旧译文）变化的帧 | 14% | 10% |

新版剩下的变化基本都是“新的一对出现”，也就是用户需要看到的新信息；上半部分的变化是新内容出现时旧内容上滑的那 0.2 秒，只要是滚动显示就免不了。另外发现，旧版的窗口本身其实没有变过大小，用户看到的“变大缩小”是字幕文字的高度在一直变。

**主要文件**：`simul_interp/ui/overlay.py`（新增 `CaptionView`、`pair_html`，重写 `Overlay` 的显示部分）、`simul_interp/config.py`、`tests/test_overlay.py`、`scripts/overlay_preview.py`

**验证**：`test_overlay.py` 重写为 8 个测试（成对出现、不插队、等太久的兜底、转义与变暗、暂定文字不影响字幕、窗口不随内容变大、旧字号只重置一次等），pytest 共 47 个通过；逐帧对比如上表。

**经验**
- 界面问题要从“人眼怎么读”出发：用户要的不是“最早看到任何字”，而是“眼睛盯着一个地方，就能读到对得上的原文和译文”。
- 这样的主观感受也可以量化：定时截图、逐帧比较，就能把“闪不闪”变成数字，改版前后可以对比。

## S13b · 当前句区域：暂定文字只在预留的空白里更新（2026-10-01）

**问题（用户的进一步意见）**：闪烁主要来自暂定文字一变，整个字幕区就跟着重新排版。能不能给正在说的这句**预留一块空白**，暂定文字只在这块空白里变化，译文的位置也先空着，翻好了直接填进去？这样周围的内容就不会动。

S13 的做法是干脆不显示暂定文字，而用户其实想看到正在说的原文，只是不要它带着别的内容跳。

**做法**
- 底部是**高度固定的“当前句”区域**，至少能放两行原文和两行译文（按最长的翻译单元估算：25 个词的法语约两行，译文约两行）。正在识别的原文在里面实时更新：已确认的部分白色，暂定的尾巴灰色；译文位置先留白，翻好了直接填进去。区域高度只在遇到放不下的长句时扩大，一对滑上去的时候才可能恢复，所以里面怎么变都不会带动上方的内容。
- 翻好的一对**先留在当前句区域**，等下一句开始（出现暂定文字，或者下一句已经确认、正在翻译）时，才平滑地滑进上方的历史。滑动的那 0.2 秒里先不画新的当前句，免得两者重叠。
- 状态提示（“正在加载识别模型”等）改成左上角的一行小字，不占字幕的位置。

**用逐帧对比发现的两个问题**（按真实边界把画面分成“历史区域”和“当前句区域”分别统计）
1. **来回跳**：第一版历史区域每分钟变化 24 次，比句子数多得多。原因是暂定文字常会短暂变空，这时按规则，最后一对又从历史退回当前句区域，暂定文字再出现时又滑上去。修复：**滑进历史是单向的**，滑上去之后就不会再退回来。
2. **整片变色**：历史的明暗级别原来取决于当前句区域里放的是译文还是暂定文字，两者一切换，整片历史就变一次颜色。修复：**明暗只看新旧**，最亮的白色只留给当前句区域，历史从次一级开始。
- 两个问题都先写了能复现它的测试（修复前失败），修复后通过。

**结果**：历史区域的变化事件从 28 次降到 17 次（约 71 秒，这段音频拆成了十几段翻译单元），基本就是每段在下一句开始时滑上去一次，这是滚动显示的最少次数。暂定文字的变化都被关在当前句区域里。

**顺带踩的坑**：统计时一开始把区域边界算错了。窗口没有真正显示出来时，Qt 不会触发调整大小的事件，读到的子控件位置是默认值。最后按程序里的摆放规则直接计算边界。

**主要文件**：`simul_interp/ui/overlay.py`（`CaptionView` 改为“当前句区域 + 历史”两部分，`Overlay.compose` 决定两部分各放什么）、`tests/test_overlay.py`、`scripts/overlay_preview.py`

**验证**：字幕窗测试 11 个（含“暂定文字怎么变，历史位置和区域高度都不变”、“不会来回跳”、“历史颜色不随当前句区域变化”），pytest 共 50 个通过；逐帧统计如上。

**经验**：用户描述的是感受（“闪”），要先弄清楚闪的是什么（内容在变，还是位置在变），再对症处理。这次的关键是把“内容变化”关在固定的区域里，而不是把内容藏起来。

## S13c · 修复 CI 在 Linux、Windows 上暴露的两个问题（2026-10-01）

**问题**：S13b 推送后，CI 在 Linux 和 Windows 上各失败了一个测试（macOS 通过）。

1. **会话记录的时间戳偶尔少 1 秒**（Linux）：秒数用 `int()` 截断，而两个很大的时钟读数相减会得到 `64.99999999953434` 这样的值，截断后就成了 64。随机试两万个时钟读数，有 1 个会出错。S10b 换成高精度时钟后，时钟读数的量级变了，这个一直潜伏的问题才碰巧暴露出来。修复：改用 `round()`。
2. **字幕窗测试在 Windows 上不稳定**：测试里的窗口从未真正显示，没显示的窗口什么时候收到“调整大小”事件，各平台不一样。Windows 上字幕区的宽度在测试中途才生效，文字折行改变，当前句区域的高度随之变化，看起来就像“历史被带动了”。这是测试的问题，不是功能的问题。修复：测试开始前先在 offscreen 平台上把窗口显示出来、处理完事件，保证尺寸已经生效。

**主要文件**：`simul_interp/transcript.py`、`tests/test_overlay.py`

**验证**：pytest 50 个通过；用随机时钟读数确认 `int()` 会截断出错、`round()` 不会。

**经验**：浮点数相减后要取整时，用 `round()` 而不是 `int()`。多平台 CI 能发现本机永远遇不到的问题。GUI 测试要先把界面状态准备好（显示、处理事件），不要依赖各平台不同的事件时机。

## S14 · 录音保存：同传时同步存一份 WAV（2026-10-01）

**问题（用户的需求）**：想在同传的同时把声音录下来，事后对照录音校对译文准不准。

**做法**
- 新增 `WavRecorder`：把送给识别模型的那一路音频（16 kHz 单声道）原样写成 16 位 WAV，每小时约 115 MB。只用标准库和 numpy，不加新依赖。
- **随时中断都不坏**：WAV 的文件头里记着数据长度，一般到结束时才填。如果只在结束时填，程序被强制退出后留下的文件头是错的，播放器打不开。所以每写 2 秒音频就把文件头更新一次，任何时候中断，文件都能正常播放，最多少最后 2 秒。
- **录音不能连累同传**：写盘出错（磁盘满、移动硬盘被拔掉）时只停止录音，在界面上提示一次，不抛异常。
- **绝不覆盖**：用 `"x"` 模式创建文件，同名文件已存在就换带序号的名字。
- **接在哪里**：给 `AudioSource.chunks()` 加了一个 `on_chunk` 钩子，每取出一块音频先交给录音一份。它在“消费音频”的线程里执行，所以录音拿到的和语音检测、识别拿到的是同一串音频，一块不多一块不少（下一步要靠这一点让记录里的时间对上录音）。没有放在“读取内录数据”的线程里：万一磁盘卡住，不能卡住采集。
- 录音和会话记录同名，方便配对：`同传_日期_时间.wav` ↔ `同传_日期_时间_译文.md`，记录的开头写着录音的路径。
- 配置 `[recording] enabled / dir`，命令行 `--no-recording`。用音频文件做输入时不录（文件本身就是录音）。

**真实内录时的一个发现**：第一次冒烟测试（不播放任何声音，运行 10 秒）录到的是 0 秒。原因不在录音代码：电脑上没有任何程序在播放声音时，macOS 的 Core Audio Tap **根本不送数据**（不是送静音），这一点和 Windows 的 WASAPI loopback 一样；播放停止后设备还会继续运行几秒（这时送的是全零的静音），然后才停。由此可知：
- 录音只包含“电脑有声音输出”的时间段，可能比实际经过的时间短；一次会话里完全没有声音时，不留空的录音文件；
- 现在会话记录里的时间是按墙上的时钟算的（还包含了加载模型的时间），和录音里的位置对不上（实测：录音里第 0 秒开始的一句，记录里标的是 `[00:12]`）。下一步（S14b）改成按音频流里的位置标时间。

**主要文件**：`simul_interp/recording.py`（新）、`simul_interp/audio/base.py`（`on_chunk` 钩子）、`simul_interp/pipeline.py`、`simul_interp/config.py`、`simul_interp/__main__.py`、`tests/test_recording.py`（新）、`tests/test_pipeline.py`（新）

**验证**
- `test_recording.py` 6 个测试：内容和格式正确（超出范围的削平）、**录到一半不收尾也能读**、不覆盖已有录音、空录音不留文件、写盘出错不抛异常且只通知一次、音频源逐块交给录音且位置和音频流时间一致。
- `test_pipeline.py` 3 个集成测试：把音频源、语音检测、识别后端都换成假的，跑完整条流水线，不需要模型，CI 上也能跑。测试音频里第 k 个词被“编码”成一段幅度为 (k+1)/100 的信号，假的识别后端靠幅度认词。检查：录音和记录同名配对、录音内容和送进去的音频逐点相同、关掉录音或用文件做输入时不录、录音写盘失败时同传照常进行。重复跑 25 次都通过（不受线程时序影响）。
- 真实内录（终端界面、模拟翻译，输出写到临时目录）：
  - 播放 10 秒测试音频后正常结束：录音 13.76 秒（约 10.5 秒声音 + 3 秒全零静音），16 kHz / 单声道 / 16 位；
  - 播放 8 秒后 `kill -9` 强制杀掉：文件仍能正常读取，实际写入 8.70 秒，文件头记到 8.06 秒。
- pytest 共 60 个通过。

**经验**
- 可能被强制中断的写入，要让文件在任何时刻都是完整的：定期更新文件头，比“结束时一次写好”稳妥。
- 附加功能不能拖累主功能：录音出错时自己停下来、报告一次，同传继续。
- 真实环境的测试能发现文档里没写的行为（没声音时系统不送数据），而且它直接影响下一步的设计。
- 集成测试可以把“答案”编码进测试数据（幅度 = 第几个词），不需要真模型就能检查端到端的结果。
- **踩的坑**：内录是系统级的。做真实内录测试时，用户自己也正好在运行同传程序，我播放的测试音频被它录了进去、显示并翻译了出来。以后播放测试音频前先确认没有别的实例在运行（已写进 `CLAUDE.md`）。

## S14b · 会话记录里的时间改成录音里的位置（2026-10-01）

**问题**：S14 发现记录里的时间和录音对不上。时间是按墙上的时钟、从程序启动算起的（包含加载模型的几秒），而录音只包含电脑有声音输出的时间段。实测录音里第 0 秒开始的一句，记录里标的是 `[00:12]`。校对时没法按时间找到录音里对应的位置。

**做法**
- 时间改用**音频流里的位置**（按采样点数算），和录音是同一把尺子。每个翻译单元记下它第一个词的时间（`TranslationUnit.audio_start`）；`UnitBuilder.add_timed` 让每个词带着自己的时间，一个单元跨好几次确认时，取第一个词的。
- 词的时间从哪来：流式识别每次输出都带着“这次识别听到了音频流的哪里”（`AsrUpdate.audio_end`）。一个词被确认时，其实已经说出口一会儿了，所以用“确认时刻 − 2 秒”估计。**没有改识别代码**：用户马上要开会，这时候不动核心部分。
- “2 秒”是量出来的：拿两段测试音频的流式识别输出，和带逐词时间戳的参照对比。32 个翻译单元里，“第一个词被确认的时刻 − 这段话真正开始的时刻”最小 0.77 秒、中位数 1.44 秒、最大 2.10 秒。取 2 秒之后，标出来的时间比真正的开头早 0～1.2 秒（97% 不晚于开头，最晚的只晚 0.1 秒）：从这个时间开始听，正好能听到这段话的开头。
- 超过一小时的时间写成 `时:分:秒`，和播放器上显示的一致；记录开头加一行说明这个时间的含义。

**主要文件**：`simul_interp/translate.py`（`UnitBuilder.add_timed`、`TranslationUnit.audio_start`）、`simul_interp/transcript.py`、`simul_interp/pipeline.py`

**验证**：pytest 共 63 个通过（新增：单元的时间取第一个词的、时间随翻译单元传到记录、记录按录音位置标时间、集成测试检查时间落在每段话开头之前一点）。测量数据如上。这一步没有再做真实内录测试：用户马上要开会，不在这时候播放测试音频、也不占用芯片跑模型，会后补做。

**经验**
- 两样东西要对得上，就让它们用同一把尺子（都按音频流的采样点数算），而不是各自看时钟再去换算。
- 参数先量再定：“往前提几秒”不是拍脑袋，用手头已有的数据量出分布再取值。
- 赶时间的时候选最小、最稳的改法。原计划是让识别给出每个词的时间，那要改核心的流式识别；实际量下来，简单的估计误差只有一秒左右，已经够用。

## S15 · 杂音时段不再输出 “Merci.”（2026-10-13）

**问题**：真实听课时，没有人对着麦克风说话、只有杂音（键盘声、提示音、远处的人声）的时段，字幕窗会冒出单独一句 “Merci.”，照样被翻译、写进会话记录。两场课的记录（约 100 分钟和 119 分钟，各两千多条）里分别有 27 处和 19 处，其中一处是 80 秒里连着出了 17 句。难点在于这句话真人也会说（下课时学生就会说），不能见到就丢。

**排查：先复现，再看是哪一层放进来的**
- 复现：从录音里切出那 90 秒，用 `--file` 回放，出了 16 句 “Merci.”（现场是 17 句）。
- 原来的猜测是“很短、很轻的杂音漏过了语音检测”。量出来正好相反：那段声音**不短也不轻**——音量 −20～−30 dBFS，和讲课差不多；带基频的帧占三到八成；Silero VAD 给的说话概率最高 1.0，一“句”能持续 9 秒。所以已有的几道门槛（整句太短、切开后说话太少）和“音量太低不识别”都拦不住它。
- Whisper 返回的置信度也分不出来：
  - `no_speech_prob`：turbo 对什么声音都给 1e-11 左右，完全没有信息量（完整版 large-v3 对同一段给的是 0.83，可惜实时用不了它）；
  - `avg_logprob`：编出来的 “Merci.” 在 −0.33～−1.13，真话在 −0.08～−1.3，混在一起。它把时间戳 token 的不确定也平均进去了，一个词的短句里时间戳占了一半。
- 试了 Whisper 自带的语言检测（“这段声音像不像法语”）。在录音上很灵：杂音上的 “Merci.” 法语概率 51 次里 49 次不超过 0.14，真人说的是 0.99～1.00。但用 macOS 的 10 种法语合成声音各说一句 “Merci.” 来验证“真的有人说”这一侧，**6 种被判成不是法语**——一个词太短，语言检测本身就不可靠。这条路否掉了。
- 最后用的信号：**解码器动笔写第一个词时，给 “Merci” 这个词多大概率**（和逐词时间戳里“词的概率”是同一种算法）。
  - 录音里看上下文像是真的 “Merci”（单独一句的 3 处，加上两句以它开头的话）：核实 8 次，0.89～0.99，完整回放时其中一处有一次是 0.75；10 种合成声音：0.87～1.00，前后多留静音也不变；
  - 杂音上编出来的：两段完整录音回放时一共核实了 203 次，189 次低于 0.7（其中 85% 低于 0.5，94% 低于 0.6）；
    通过的 14 次里，11 次属于最后留下来的 5 句和两句以 Merci 开头的话（0.72～0.99），另外 3 次（0.70～0.80）只通过了一次，下一次识别没再通过，没有被确认；
  - 而且在杂音上它很不稳定：同一段缓冲区往后挪 1～32 毫秒，结果在 0.30～0.72 之间跳；真话上纹丝不动。所以不能核实一次就一直算数，每次识别都要重新核实。

**做法**
1. 识别后端加 `word_probability(audio, word)`：只听这段音频时，模型认为第一个词就是 `word` 的概率。MLX 后端直接跑一次编码器、看解码器第一步的输出（约 0.35 秒，和识别一次差不多）；faster-whisper 后端用逐词时间戳里自带的词概率（没在 Windows 真机上跑过）。
2. `StreamingTranscriber` 只在“**整个结果只有 Merci.**（可以连着重复），缓冲区里没有别的已确认内容”时去核实，概率低于 0.7 就判为编的：
   - 这一次不显示、不确认；
   - **连着两次**都是编的，就把这段声音从缓冲区里扔掉（留最后 0.2 秒，万一正好有人开口）。不扔的话下一次还会再编，后面真有人说话时，开头还会被带上一句 “Merci.”；
   - 说完时（VAD 判定结束），如果上一次是被拦下的，要对着完整的一句**再识别、再核实一次**。原因是实测发现：词刚说到一半就识别的那一次，有的声音概率只有 0.3～0.5，听完整才到 0.87；而核实本身要 0.35 秒，等它做完往往已经直接到“说完”了，不补这一次，真的 “Merci.” 就丢了。
3. 范围故意收得很窄：只管单独的 “Merci.”。“Merci beaucoup.”“Merci à tous.” 不核实——没有观察到它们被编出来，而录音里正好有一句这样的话（很轻，看上下文是真的），按这个办法概率只有 0.44～0.50，会被错杀。夹在别的话中间的 “Merci.” 也不核实（核实的是“这段音频的第一个词”，前面有别的话就不是这个问题了）。
4. 后端没有 `word_probability`（比如测试用的假后端）时不核实，行为和以前一样。

**主要文件**：`simul_interp/asr/streaming.py`（`_is_made_up`、`_drop_made_up`、`finish`）、`simul_interp/asr/common.py`（`is_filler`）、`simul_interp/asr/mlx_backend.py`、`simul_interp/asr/faster_whisper_backend.py`、`tests/test_streaming.py`、`tests/test_windows.py`

**验证**
- 单元测试新增 7 个，pytest 共 70 个通过。假后端模拟“整段都是杂音、VAD 一直标成在说话、每次都识别成 Merci.”：既不确认也不显示，缓冲区不会越攒越长；最后一次识别编出来的也不确认；真的 “Merci.” 照常显示和确认；“太早被拦下、之后直接说完”的真 “Merci.” 会补核实一次；杂音被扔掉后紧接着的真话一个词不少。临时关掉核实，这 5 个行为测试全部失败；单独去掉“说完时补核实一次”，对应的那个测试失败。
- 那 90 秒片段，真实命令行实时回放：单独的 “Merci.” **16 句 → 0 句**。
- 两段完整录音各回放一遍，和当时现场的记录比（见下面“回放的办法”）：单独的 “Merci.” **27 句 → 4 句**、**19 句 → 2 句**，合计 46 → 6。剩下的 6 句：3 句模型把握很高（两次核实里至少一次在 0.96 以上，包括下课时那句），2 句在 0.72～0.87 之间（说不准是很轻的真 “Merci” 还是漏网的），1 句夹在一句话中间（不在核实范围内）。连着出了 17 句的那 80 秒，回放里核实了 44 次、扔掉声音 12 次，只留下紧跟在老师一句话后面的 1 句（把握 0.87）。下课时听得清的那句 “Merci.”（0.98）和紧接着一句以 Merci 开头的道别都在。
- 没有误删正常句子：两段回放里一共有 115 处出现过被拦下的 “Merci.”，现场记录里这些地方前后几秒共有 306 句别的话，自动比对有 13 句在回放里找不到原样的对应，逐句看过：11 句是个别短语的识别结果不同（两次运行的时序不一样，本来就会有），2 句是那 80 秒杂音里编出来的别的句子，这次没再出现。整体上，回放的文字和现场记录有 94.4% 和 98.0% 的词对得上。
- 没有带来别的副作用：句末有标点的记录占比 90% → 89%、87% → 87%，含逗号的占比 34% → 33%、39% → 38%，没有出现连续丢标点的片段（中途有一版在拼接的试验片段上出现过一次，所以专门统计了这一项）。
- 回放的办法：按 1 倍速回放两段录音要 3.6 小时，而且结果受机器快慢影响。所以写了个一次性的回放脚本（没进仓库）：照着 `AsrRunner` 的循环喂音频，但时钟是算出来的——每次识别的耗时用实测拟合的公式（0.325 秒 + 每个字符 1.1 毫秒，核实一次 0.35 秒）。同一段 90 秒片段，它和真实命令行回放的结果一致（修复前 17 句对 16 句）。“修复前”用的是现场的记录；另外把现场每一处 “Merci.” 前后 35 秒拼成两个试验片段，用新旧代码各跑一遍对照，定方案时主要靠它。
- `bench-asr` 两段合成语音，修复前后交替各跑 3 轮取中位数：fr_meeting 显示延迟 0.68 → 0.69 秒、确认延迟 1.34 → 1.32 秒、句末延迟 0.99 → 1.05 秒，词错误率都在 5.6%～6.2%；fr_continuous 0.80 → 0.83、1.43 → 1.47、1.01 → 1.27 秒（三轮的范围是 1.00～1.32 和 1.06～1.32，重叠），词错误率 4.9%（修复后有一轮 5.6%，差一个词）。两个版本各轮之间的差别比版本之间的差别大：这台无风扇的电脑连续跑了几小时模型，每次识别的耗时在 0.44～0.64 秒之间飘，延迟跟着它走。结论是没有可测出的变化。
- 代价：一句话以 “Merci” 开头时（比如 “Merci à tous pour…”），第一次识别的结果正好是单独的 “Merci.”，要多花一次核实，这句话的第一个词晚出现约 0.35～0.5 秒。

**没有解决的**
- **连续的、像人声的杂音时段，还会出别的短句。** 那 80 秒单独切出来回放时，“Merci.” 没有了（不同时序跑了几遍，0～1 句），但别的编出来的短句从修复前的 1～3 句变成了 5～8 句：以前这些声音大多被 “Merci.” “消化”掉了，现在偶尔会连着两次识别成同一句别的话，就被确认了。放在完整录音里回放时这一段一句别的也没出，可见很看运气（前面说过什么、识别的节奏都有影响）。总数是降了，但剩下的这些看起来更像真话，需要知道。它们和 “Merci.” 是同一个根因（语音检测把这种声音当成了说话），但没有 “第一个词的概率” 这么干净的判据：摸底时试过语言检测，正常讲课的片段里，缓冲区不到 0.9 秒时有 48% 被判成不是法语，0.9～1.5 秒时 21%，拿来当门槛会误伤太多真话。
- 特别含糊、特别轻的真 “Merci.”（模型自己的把握不到七成）会被丢掉。下课时除了听得清的那一句，现场记录里后面还有两句，回放时把握只有 0.1～0.5，被拦下了，没法确认它们是不是真的。

**经验**
- 先量再猜。“短促的杂音漏过了 VAD”听起来很合理，量出来却是“又长又响、VAD 很有把握”。要是照着猜测去加时长和音量门槛，一句也拦不住。
- 模型返回的“置信度”先看它在自己用的这个模型上有没有信息量：turbo 的 `no_speech_prob` 是个常数，`avg_logprob` 被时间戳稀释了。真正有用的数要自己去问模型。
- 找判据时，正反两类样本都要有。语言检测在“杂音”这一侧表现完美，是特意造的“真 Merci.”样本（合成语音）把它否掉的；录音里真的 “Merci.” 只有几句，不造样本根本发现不了。
- 判据不稳定时（杂音上同一段声音挪几毫秒概率就变），不要缓存结论，每次重新问；同时把“一次没通过”和“确认是杂音”分开——前者只是先不显示，后者才扔数据。
- 回放两小时的录音来验证时，结果会受识别快慢影响（机器一忙，识别的节奏就变了）。这次用的回放脚本（一次性的，没进仓库）把“每次识别花多久”换成一个拟合出来的固定公式，结果只取决于代码和音频，才能放心比较。

## S16 · 没说完的半句话先等一等（2026-10-13）

**问题（用户的意见）**：两句话之间的间隔判得太短。说话人常常说了半句、停下来想一想再接着说，同传却把它切成两句，各翻各的，译文是碎的。

**先量再改**（四段真实的会议和课堂录音，共 4 小时 23 分；录音只在本地用，这里只写统计数字）
- 只跑语音检测，统计两段话之间的停顿，共 3268 次：58% 不到 1 秒，76% 不到 1.5 秒，84% 不到 2 秒。
- 对照当时的同传记录：“一段话的最后一个翻译单元”里，34%（904 / 2651）结尾不是句号或问号，其中省略号结尾的占三分之二。这些就是被切开的半句。
- 它们后面的停顿很短。语音检测判定“说完”之后再等 0.6 秒，63% 的说话人已经接着说了；等 1.0 秒是 80%，1.5 秒 87%，2.0 秒 92%。

**为什么不把“静音多久算说完”（400 毫秒）调大**：那样每一句话的确认都要多等，完整的句子也跟着变慢。出问题的只是“没说完的半句”，所以只让半句等。

**做法**
1. 一段话说完时，剩下的词如果凑不成一句（结尾不是 . ? !），先不送去翻译，留在“正在说”那一行（界面上是已确认的白字）。说话人接着说，新的词直接接在后面，凑成整句再翻。
2. 安静超过 `translate.incomplete_wait_s`（默认 1.5 秒）还没有下文，才把这半句送去翻译；设成 0 就和以前一样说完就翻。
3. “说话人又开口了”由语音检测直接通知翻译阶段，比识别结果早近一秒。否则会出现人已经在说了、前半句却到点被送走的情况。实现上记的是“开口了几段 − 处理完几段”这个数，而不是一个“是否在说话”的开关：下一段话可能在上一段的识别结果处理完之前就开始了，开关会被后到的结果错误地关掉。
4. **省略号不再算句子结束**。Whisper 用 “...” 表示说话人拖着音想词，以前把它当句号，一遇到就切。现在短的半句不在省略号处切，攒到 14 个词以上才切（够长了，可以先翻）。
5. 一口气 25 个词还没有句号、必须切的时候，切在最后一个逗号或省略号之后，而不是正好第 25 个词那里。实测硬切会把词组从中间切开，比如切在主语和动词之间。
6. 等的时候不白等：离到点还有 0.8 秒时，把这半句先送去投机翻译，真到点时译文已经现成。多数情况下说话人在这之前就接着说了，这次请求也就省了。
7. 顺带：“M.” 这样的单字母缩写不再被当成句子结束；退出时还留着的半句会送去翻译，不会丢。

**主要文件**：`simul_interp/translate.py`（`UnitBuilder.cut`、`TranslationStage` 的等待逻辑）、`simul_interp/asr/runner.py`（`on_speech_start`）、`simul_interp/pipeline.py`、`simul_interp/config.py`

**验证**
- 取一段真实会议录音里说话最犹豫的 4 分钟，按真实速度回放：

| | 段数 | 停顿时被切出来的半句（不满 8 个词、结尾不是句号或问号） |
|---|---|---|
| 当时开会的实际记录（旧版） | 99 | 37 |
| 新规则，不等（`incomplete_wait_s = 0`） | 67 | 7 |
| 新规则，等 1.5 秒（默认） | 56 | **0** |

  每段的词数中位数从 8 个变成 10 个。旧版那一行是当时的实际运行，和回放不是同一次识别，只能看量级；后两行是同一份代码、同一段录音。
- 一个例子（句子是编的，真实录音里的话不写进日志）：“Alors je voudrais vous présenter aujourd'hui le...” 说到这里停下来想词，再接 “le plan du projet.”。旧版切成两段各翻各的，现在是完整的一段。
- 新增 8 个单元测试（等待、取消、到点送出、开口的先后顺序、退出不丢、提前投机翻译、两条切分规则）和 1 个集成测试（假音源里“说半句、停一秒、接着说完”）。pytest 共 79 个通过。
- 完整句子的延迟不受影响：它们的确认和送翻译走的还是原来的路。

**没有解决的**：逗号处的切分（攒够 8 个词遇到逗号就先送前半句）有时切得别扭，比如切在 “Oui,” 后面。这是为了压低长句的延迟而设的，这次没有动。

**经验**
- 先量再改：半句话后面的停顿中位数只有 0.4 秒，所以等 1.5 秒就够，不用等很久；这个数是量出来的，不是猜的。
- 只改出问题的那一类情况，不动影响全局的阈值。
- 多线程里，“状态”用计数比用开关稳：两个线程报告事件的先后可能和事件发生的先后不一样。
- 规则改了要用真实数据看结果。第一版把省略号完全不当切点，结果长句被硬切在词组中间；看了回放的输出才发现，于是加上“超长时切在最后一个停顿处”。

## S17 · 字幕窗可以往回翻看（2026-10-13）

**问题（用户的需求）**：字幕窗只显示最近三对，过去了就看不到。想加一个滑动条，能回头看之前翻译的句子。

**做法**
- 字幕窗保留最近 500 对（`ui.scrollback`；以前只记 30 对、显示 3 对），窗口里放得下多少就显示多少。原来的 `ui.max_lines` 取消了，旧的 config.toml 里还写着也不报错，只提醒一句。
- 往回翻有两个办法：在字幕窗上滚滚轮（触控板双指滑动是按像素走的，跟手），或者拖右边的滑动条，点轨道直接跳过去。滑动条平时很淡，回看和拖动时变亮。
- **回看时眼前的内容不动**：新的一对照常加在下面，同时把“翻了多少”加上它的高度，两相抵消；这时不做滑上去的动画。底部的当前句区域照常显示正在说的话，不会因为回看而漏掉。
- 顶部出现一行提示“正在回看 · 点这里回到最新”，点它或者滚回最底下都能回到最新；右键菜单里也有“回到最新字幕”。
- **明暗改在画的时候决定**。以前“越旧越暗”是把颜色写进每一对的文字里，新旧一变就要改文字、重新排版。现在所有历史用同一种颜色，画的时候按新旧设不同的不透明度；回看时全部按最亮画，几百对都不用重排。
- 性能是量过再定的：一对原文译文排版一次约 0.35 毫秒，3000 对要占 100 MB 内存，所以没有无限保留。窗口变宽窄时，60 对以内当场全部重排；更多时拖动期间只排看得见的，停下来 0.15 秒后再排全部。字幕窗每 50 毫秒的定时检查，在没有变化、也没有正在等的译文时直接返回。
- 顺带：两个翻译单元几乎同时发出时（S16 之后会有，其中一个是等够时间送出的半句），通知到达的先后可能反过来，字幕窗按编号排回去。

**主要文件**：`simul_interp/ui/overlay.py`（`CaptionView` 的滚动，`Overlay` 的滚轮和滑动条）、`simul_interp/config.py`

**验证**
- 字幕窗的测试从 11 个增加到 18 个：能翻到头、回看时位置纹丝不动（误差小于 0.01 像素）、滚轮 / 滑动条 / 顶部提示三种操作（用 Qt 的测试工具发真实的鼠标和滚轮事件）、超过上限只留最近的、窗口变窄后重新折行、空闲时不做事、乱序到达按编号排好。pytest 共 87 个通过。
- 把字幕窗渲染成图片看过三种状态：停在最新、往回翻、翻到最旧。没有在真实屏幕上用手操作过（开发时不想在用户的屏幕上弹窗口）。

**经验**
- “全部保留”听起来最省事，量一下才知道代价（内存、重排时间），然后再定上限。
- 把“随状态变的外观”（明暗）和“内容”（文字排版）分开，状态变了就不用动内容。
- 把滚动位置定义成“离最新有多远”，新内容进来时同步调整，比事后去修正位置简单，也不会闪。

## S18 · 字幕窗可以收起成一个小条（2026-10-13）

**问题（用户的需求）**：有时候不想看字幕，但不想退出程序，希望字幕窗能收起来（最小化）。

**为什么不用系统的最小化**：字幕窗没有标题栏，程序也不在程序坞里显示图标（这样才能浮在全屏的会议和视频上面），系统的最小化在这里用不了，收进去也找不回来。所以自己做：缩成一个小条留在屏幕上。

**做法**
- 右上角加一个“–”按钮（在小圆点左边）。点它，窗口缩成原来位置左下角的一个 176×30 的小条，上面只有“正在听”的圆点和一行“同传字幕 · 点击展开”。右键菜单和菜单栏图标里也有“收起 / 展开字幕窗”。
- 小条可以拖动。按下到松开鼠标移动不超过 4 个像素算点击（展开），超过算拖动。展开时大小和收起前一样，左下角跟着小条走，并且不会超出屏幕。
- 收起的时候识别、翻译、会话记录、录音照常进行，只是不排版、不画字幕；展开时把期间的句子一次补上。
- 收起着退出的话，记下的是展开后的位置和大小，下次启动是展开的。
- 背景调得很透明时，小条的背景至少保持 45% 不透明，否则在亮的画面上找不到它。

**主要文件**：`simul_interp/ui/overlay.py`（`set_collapsed`、鼠标按下 / 松开的判断、小条的绘制）

**验证**
- 新增 2 个测试，用 Qt 的测试工具发真实的鼠标事件：点“–”收起、小条的大小和位置、收起期间来的句子展开后都在、点小条展开回原来的位置和大小；拖动小条不会展开、展开后左下角跟着小条、收起着保存设置记下的是展开的大小。pytest 共 89 个通过。
- 把小条和带“–”按钮的字幕窗渲染成图片看过（README 的配图已更新）。没有在真实屏幕上用手操作过。

**经验**

## S19 · 流水线支持暂停 / 继续和运行中换语言（2026-10-13）

**问题（用户的需求）**：想要一个界面来切换语言、开始 / 暂停监听。做界面之前，流水线本身要先有这些能力：以前它一启动就一直听到退出，语言写死在配置里。

**做法**
- **暂停 / 继续放在音频源这一层**：暂停后送来的音频直接丢掉，“已经送出多少采样点”的计数也跟着停住。这样录音里没有暂停的那段空白，音频流时间仍然等于录音里的位置，S14b 做的时间对齐不受影响。
- 暂停前先补一小段静音（判定说完所需的静音 + 0.3 秒）：正说到一半的话要靠它才能被语音检测判定为“说完了”，否则这半句会悬着，等到继续之后才出来。继续时在会话记录里留一行“暂停后从这里继续”。
- 用文件模拟时，暂停是让文件停在原地、继续后接着放，暂停的时间不算进播放进度（否则继续后会快进去追）。
- **换语言不用重新加载模型**：Whisper 是多语言的，语言只是每次识别时的一个参数。但有三样东西还“记着”旧语言，要一起处理：识别用的上文提示词（旧语言写的，通过事件队列交给识别线程清掉）、翻译提示词里的源语言名、翻译时附带的上文。记录里留一行“12:34 起：英语 → 简体中文”，插在下一个翻译单元之前。
- 源语言只开放按空格分词的语言（法、英、西、德、意、葡）。流式识别是按“词”逐个确认的，中文、日语这类不分词的语言要换一套做法，这次没做。目标语言只是提示词里的一个名字，不限。
- `Interpreter` 有了明确的状态：loading（在准备）→ listening（在监听）⇄ paused（暂停）→ ended（结束），界面只需要看这个状态。新增 `ui.autostart`（默认 true）和 `run --paused`，可以启动后先不听。
- 翻译提示词里原来写死的“法语”改成当前的源语言。

**主要文件**：`simul_interp/audio/base.py`（`pause` / `resume` / `position`）、`simul_interp/audio/file_source.py`、`simul_interp/asr/runner.py`（`set_language`）、两个识别后端（`set_language`）、`simul_interp/pipeline.py`、`simul_interp/translate.py`、`simul_interp/transcript.py`（`note`）、`simul_interp/languages.py`（新）

**验证**
- 新增 7 个测试，pytest 共 96 个通过。其中一个是完整流程的暂停测试：假音源先送第一句，暂停，暂停期间送第二句（不识别、不录、音频流时间不走），继续后再送一遍（照常出来），最后检查录音长度等于音频流时间、记录里说明行的位置对。
- 真实模型：按默认配置（法语）启动，调用 `set_languages("en", …)` 后送入一段英语合成语音，识别出 “Good morning everyone, and thank you for coming to this meeting.”，记录里有换语言的说明行。
- 没有验证的：真实内录时的暂停（只用假音源和文件源测过）；英语以外的其他语言没有实际跑过；faster-whisper 后端（Windows）的 `set_language` 只是改一个属性，没有在真机上跑过。

**经验**
- 暂停放在最上游，并且让“时间”一起停，下游所有依赖时间对齐的东西（录音、记录里的时间）都不用改。
- 运行中换一个参数之前，先列出“还有谁记着旧值”。这里是上文提示词、翻译的上文、提示词里的语言名。

## S20 · 应用前端：控制面板（2026-10-13）

**问题（用户的需求）**：做一个应用前端，能切换语言、开始 / 暂停监听。以前只有一个没有按钮的字幕窗，所有设置都靠改配置文件和命令行参数。

**做法**
- 新增控制面板（一个普通的小窗口）：两个下拉框选“说的语言 → 译成的语言”，一个大按钮开始 / 暂停监听，一行状态（正在准备 / 正在监听 / 已暂停 / 已结束），下面是“显示字幕窗”、“收起 / 展开字幕窗”、这次的录音和记录的文件名、“打开所在文件夹”和“退出”。
- **面板只是遥控器，不自己记状态**：它每 0.2 秒看一眼流水线和字幕窗的真实状态，把按钮和文字改成对应的样子。所以状态是从哪里变的（面板、字幕窗的右键菜单、菜单栏图标）都不要紧，面板显示的总是实际情况；模型还在加载时按钮是灰的。
- 界面的启动代码从 `overlay.py` 搬到新的 `ui/app.py`：主线程跑 Qt 界面，流水线在后台线程里跑，结果通过 Qt 信号回到主线程；界面对流水线的操作（暂停、换语言）直接调用 S19 做好的方法。
- 这个程序不在程序坞里显示图标（这样字幕窗才能浮在全屏的会议上面），普通窗口默认不会自己跑到前面来，所以显示面板时要明确地把程序激活；面板关掉后能从字幕窗的右键菜单和菜单栏图标找回来。
- 启动更省事：不写子命令就是 `run`（`python -m simul_interp`）；加了可以双击的 `启动同传.command`（macOS）和 `启动同传.bat`（Windows）。
- 面板上选的语言只管这一次，不写回配置文件：配置文件是用户自己写的，程序不去改它。
- 顺手修了一处识别问题（端到端检查时发现）：暂停后继续时，把给识别当提示用的上文清掉。暂停前后的声音接不上，留着上文的话，继续后的第一句容易被模型照着上文“复述”——实测继续后的 “…du système de reconnaissance vocale.” 被识别成了 “du a terminé la version.”，清掉上文后识别正确。

**踩的坑：点“退出”时灵时不灵**
- 一开始为了“点面板的关闭按钮只藏起来、不退出”，重写了面板的 `closeEvent`，在里面拒绝关闭并把自己藏起来。结果自动测试偶尔卡死：程序该退出的时候不退出。
- 原因：Qt 退出之前会先把所有窗口挨个关一遍，有一个窗口拒绝关闭，这次退出就作废。而挨个关的顺序每次不一样（窗口放在一个哈希集合里）：字幕窗先被关，再轮到面板时面板把自己藏了起来，Qt 一看没有窗口还开着，就照常退出；面板先被问到，它拒绝了，字幕窗还开着，退出就被取消。所以大约一半的时候退不掉。
- 改法：不重写 `closeEvent`。窗口被关闭时 Qt 默认就只是把它藏起来，而“最后一个窗口关了就退出程序”已经在启动时关掉了，这正好就是想要的行为。
- 第一次排查时猜错了原因（以为是后台线程发的“结束”信号早于事件循环启动而丢了），改了也没好。后来写了一个脱离 pytest、反复启动退出、带 3 秒看门狗的小脚本，看到“信号明明到了，但程序没退出”，才找对方向。

**主要文件**：`simul_interp/ui/panel.py`（新）、`simul_interp/ui/app.py`（新）、`simul_interp/ui/overlay.py`（右键菜单加“控制面板”、`activate_app`）、`simul_interp/__main__.py`（默认子命令、`--paused`）、`simul_interp/asr/runner.py`（`reset_context`）、`启动同传.command`、`启动同传.bat`

**验证**
- 新增 12 个测试，pytest 共 108 个通过（完整测试连跑 6 遍、流水线测试连跑 40 遍都稳定）。面板的测试用假的流水线和真的字幕窗；入口的测试把整个界面从启动跑到退出，其中“点退出按钮真的能退出”重复跑 4 次（关窗口的顺序是随机的，多跑几次才碰得到），并且在旧写法下确实会判失败。入口测试里加了保险：10 秒还没退出就强行结束并判失败，而不是让测试一直卡着。
- 真实模型 + 真实界面跑了一遍完整流程（offscreen，不上屏、不出声；输入是法语合成语音的文件，模拟翻译）：暂停着启动（等 2 秒，一句都没有）→ 点“开始监听”→ 14 秒后点“暂停监听”（之后 5 秒句数和音频位置都不再变）→ 点“开始监听”继续 → 收起、展开字幕窗 → 往回翻、回到最新 → 文件放完后自动退出。按钮的文字、状态、提示每一步都对，记录里“暂停后从这里继续”的位置也对。
- 真实的 macOS 窗口系统下跑了一遍约 12 秒的短流程（文件输入，不内录）：面板出现并且在最前面、开始 / 暂停、收起 / 展开字幕窗、关掉面板后从字幕窗菜单叫回来、点“退出”正常退出。这一步是必须的：把程序切到前台的那段代码只在真实窗口系统下才执行，offscreen 的测试跑不到它。按钮是程序替用户点的，不是真的用鼠标。
- 合并 S15 之后把上面的完整流程又跑了一遍，结果一致。看到一个小问题：从半句话中间继续时，继续后的头一段有时没有标点，会连成较长的一段一起翻译（两次里一次正常断句，一次连到了下一句）。
- 没有验证的：没有真的用鼠标在屏幕上点、拖过（滑动条和小条的拖动只有自动测试）；真实内录时的暂停；“打开所在文件夹”按钮；双击启动的两个脚本（`.command` 只检查了内容和可执行权限，`.bat` 没有在 Windows 上跑过）。

**经验**
- 想要“关窗口不退出”，先看框架的默认行为是不是已经够了；在关闭事件里说“不”，会连带挡住框架自己的退出流程。
- 偶发的卡死，先想办法把它变成“看得见的失败”（看门狗、超时后打印状态），再找原因；凭猜测改一处、重跑碰运气，很容易改错地方。
- 界面不存状态、只照着真实状态画，按钮就不会和实际情况对不上。

## S21 · 边说边译：话还没说完就出中文（2026-10-13）

**问题（用户的反馈）**：实时性太差。看到法语的时候就应该能看到中文，现在却要等说话人把一句很长的话说完，中文才出来，不符合做这个工具的初衷。

**先量**
- 以前的延迟指标是“一句话说完 → 出现中文”（约 1 秒），它量不出这个问题：句子越长，句子开头的词等得越久，而这段等待不在指标里。
- 新加一个指标，贴着用户的感受定义：**一个法语词出现在屏幕上 → 屏幕上出现包含它的中文**，对每个词算一次。`bench-pipeline` 现在会打印它。
- 基线（真实翻译接口，按真实语速回放）：合成的会议样例中位数 2.1 秒、最慢 7.4 秒；用户实际测试的一段 30 秒录音中位数 4.3 秒、90% 在 15.2 秒以内——那段录音只切成了 4 段，第一段攒了 25 个词（约 13 秒）才送去翻译。
- 原因有两层。设计上，字幕窗里“正在说的这一句”下面一直是空的，中文要等这句话切出来才有（S13 为了不闪，特意不显示还会变的译文）。那次测试里更糟：识别模型从半句话中间开始听时一直不加标点，而切句完全靠标点，只能攒到上限 25 个词才切。S16 让半句话多等一会儿，也让它更慢了。

**做法：当前句每多几个词，就先译一版草稿显示出来**
1. 正在说的这句话（已确认的词 + 暂定的词）够 3 个词就出第一版草稿，之后比上一版多 2 个词就出下一版，显示在当前句的原文下面。整句定下来之后照常出正式译文，会话记录里存的是正式译文。
2. **同一时刻只请求一版**。请求一次约 1 秒，这期间多出来的词等它回来再一起译。这样请求的节奏自然跟着翻译服务的速度走（说话时大约每秒一次），服务慢了也不会越积越多。
3. **把上一版草稿交给模型，要求“译对的照抄，译错才改”**。不给的话，模型每次都会换个说法（“然而”变“不过”、“花了”变“花掉了”），屏幕上整行都在变。用三句合成的句子、每 3 个词请求一次实测：不给上一版，24 次里 20 次把前面改了；给了之后 24 次里 20 次是纯粹往后接着长，剩下 4 次是确实该改。试过更严的“一个字都不许改”：更稳，但译文会别扭甚至出错（前面译死了，后面的词只能硬接），所以没用。
4. **草稿不带上文**。带上的话，模型常把上文也当成“这句话”的一部分译进来，有时甚至只译了上文（样例里出现过：原文才说了 “Et à la semaine”，草稿却是前面那句“我建议组织一次演示”的译文）。草稿只显示一两秒，用不着上文；正式译文照常带。要译的半句用「」框起来。
5. **草稿不译最末尾那个暂定词**。量了一下暂定文字有多不可靠：最末尾那个词有 28% 之后会变，再往前的约 15%。少译一个词，换来少显示很多“先错后改”的字。
6. **新的一版追上旧的长度之前，先显示旧的**。译文是一个字一个字来的，直接换的话这一行会先缩短再变长，看着是在闪。
7. 这句话切出来的那一刻，正式译文还没到：让这个翻译单元先接着显示草稿（颜色暗一点），正式译文追上草稿的长度再换。否则中文会先消失、过一秒再从头出现。下面已经有草稿的句子也不再占着当前句区域等正式译文，下一句一开始就让位，正式译文到了在历史里原地换掉。
8. 原有的投机翻译（看上去说完了一句就先翻）保留，但只在后台准备、不显示：暂定文字末尾的句号常常是识别模型顺手加的，这时把“整句的译文”显示出来，是一句已经收尾的错话。它的作用变成“原文确认时，正式译文已经翻好，直接换上”。
9. 顺带修了一个会让界面卡住的问题：翻译服务繁忙时不报错，而是让请求一直挂着（不时发来一行空的“保持连接”），实测能挂几分钟。给“等第一个字”设了期限：草稿 4 秒（过了就没用了，放弃、出下一版），正式译文 12 秒，一个字都没出来就失败的话重试一次。

**主要文件**：`simul_interp/translate.py`（草稿的提示词、`_want_draft` / `_next_draft` / `_run_draft`、显示规则 `_offer_live`、翻译单元的 `placeholder` / `shown`）、`simul_interp/ui/overlay.py`（当前句下面显示草稿）、`simul_interp/bench.py`（新指标 `display_lag`）、`simul_interp/config.py`（`live_draft`、`draft_min_words`、`draft_step_words`）

**验证**（真实翻译接口，按真实语速回放；每格是 中位数 / 90% / 最慢，单位秒）

| 一个法语词出现 → 包含它的中文出现 | 关掉边说边译 | 边说边译 |
|---|---|---|
| 合成的会议样例（62 秒） | 2.1 / 5.5 / 7.4 | 1.2 / 2.1 / 3.3 |
| 合成的连续讲话样例（51 秒） | 2.3 / 4.6 / 6.4 | 1.4 / 2.0 / 3.7 |
| 用户实际测试的 30 秒录音 | 4.3 / 15.2 / 16.4 | 1.5 / 2.7 / 5.2 |

- 老指标（说完 → 出现正式译文）没有变差：会议样例中位数 1.1 秒和 1.3 秒，在两次运行之间的波动范围内。
- 草稿稳不稳：会议样例里当前句下面的中文变了 69 次，其中 65 次是接着往后长，4 次改了前面的字。
- 请求数：会议样例从 52 次变成 94 次（多出 42 次草稿），用户那段录音从 13 次变成 32 次。
- 新增 13 个测试，pytest 共 121 个通过。用真实的程序入口（offscreen）跑了一遍会议样例，每 0.6 秒截一张字幕窗的图，逐张看过草稿跟着原文往下长、切句后换成正式译文的过程。
- 没有验证的：没有在真实屏幕上、真实内录时看过（上面都是用文件回放）；法语以外的语言；长时间运行时的请求费用。

**没有解决的**
- 草稿是照着还没确认的文字译的，识别模型一开始听错的词，草稿也跟着错，一两秒后才改过来（比如开头那句常被先听成“感谢观看这个视频”）。这是“早显示”的代价，关掉 `live_draft` 就回到只显示确定的译文。
- 延迟的下限现在是翻译服务出第一个字的时间（约 0.9 秒），再加上等词稳定、等上一版回来。想再快，要么同时请求两版（请求更多），要么换首字更快的翻译服务或本地模型。
- 识别模型不加标点时仍然会攒到 25 个词才定稿。有草稿之后中文不受影响，只是正式译文来得晚、一段很长。

**经验**
- 指标要量用户说的那件事。“说完到出现中文”一直很好看，但用户感受到的是“看着法语等中文”，这两个不是一回事；换了指标，问题才看得见、改了才知道有没有用。
- 让大模型在流式场景里“接着上一次的输出往下写”，比每次重新生成稳得多；但不能要求一字不改，要留出改错的余地。
- 给模型的参考材料（上文）和要它处理的内容要分得很清楚，否则它会把参考材料也处理了。任务本身很短的时候，干脆不给参考材料。
- 外部服务“慢”和“坏”要分别处理：坏了会报错，慢了却可能一直挂着。凡是有时效的请求，都要自己定一个期限。

## S22 · 字幕窗拖边改大小、窗内调字号（2026-10-14）

**问题（用户的需求）**：想直接用鼠标拖拽改变字幕窗的大小，文字跟着填满放大或缩小后的窗口；字号也想直接在字幕窗上调。原来只有右下角一个 16×16、几乎看不见的拉手，字号只能从右键菜单里调，用户没找到。

**做法**
- **任意边、角都能拉**：离边 6 像素以内按住拖是拉这条边，离角 16 像素以内是拉角，右下角 16×16 整块都算（那里画着拉手）。被拉的边跟着鼠标走，对面的边不动。去掉了 Qt 自带的拉手（QSizeGrip），改成自己判断：无边框窗口在各平台上的表现不一样，自己算更可控，也能测。
- **看得出该拉哪里**：鼠标移到字幕窗上时描出窗口的边框、画出右下角的拉手；停在边或角上换成对应的调整大小的光标。背景调得很透明时，这是唯一能看出窗口有多大的办法。
- **文字填满新的大小**：字号不跟着窗口变，文字按新的宽度重新排（S17 已有的重排）：拉宽了每行放得下更多字，拉高了上面能看到更多历史。字号单独调——用户把两件事分开提的，窗口大小和字号绑在一起的话，想要“窗口小一点但字不变小”就做不到。
- **最小尺寸**：最窄 320 像素，最矮刚好放得下当前句区域（两行原文、两行译文），随字号变：字号调大后窗口太矮的话，自动变高。收起成小条时取消限制。
- **在字幕窗上调字号**：鼠标移到窗口上，右上角“收起”按钮左边出现 A− / A+；按住 ⌘（Windows 上是 Ctrl）滚动滚轮也行，触控板一点一点给的量攒够一格才变；macOS 触控板双指捏合，攒够 8% 变一档（2 像素）。改完左上角显示“字号 26”一秒多。字号和拉完的窗口大小都马上存下来，不等退出。

**主要文件**：`simul_interp/ui/overlay.py`（`_edges_at`、`_resize_to`、`_font_buttons`、`zoom_by`、`minimum_height`、绘制边框和拉手）

**验证**
- 新增 6 个测试，pytest 共 127 个通过：用 Qt 的测试工具发鼠标事件，拉右边、左下角、上边、右下角，检查新的位置和大小（对面的边不动）；拉过头停在最小尺寸；停在边上、角上、中间时的光标；拉宽拉高后每一对折的行变少、能看到的历史变多、字号不变；点 A− / A+、⌘ + 滚轮（含触控板的小增量）、不按 ⌘ 时滚轮仍是翻历史、双指捏合；小条不能拉。
- 在真实的 macOS 窗口系统下跑了一遍（程序代替鼠标）：700×240 的窗口拉右边 +300、拉上边 +120、点两次 A+、再把右下角往里拉过头，大小和位置都对，最后停在当前字号下的最小高度；截图看过边框、拉手、A− / A+ 和字号提示。
- 没有验证的：真的用手拖（光标在真实屏幕上换没换、边缘好不好抓）；触控板双指捏合（只测了收到捏合之后的计算，没有真的捏过）；Windows。

**经验**
- 功能做了但用户找不到，等于没做：原来的拉手太小、和背景一个颜色。可发现性（鼠标移上去就看到边框、光标变样）和功能本身一样要紧。
- 两个需求能分开就分开：窗口大小和字号是两件事，各自有直接的操作，比“拉窗口顺便缩放字”更好控制。

## S27 · Windows 实测：显卡识别用 pip 装的 CUDA 12 库（2026-10-14）

**问题**：第一次在 Windows 真机上跑。这台电脑装的是 CUDA Toolkit 13.0，没有 cuDNN。ctranslate2 4.8.3 要的是 `cublas64_12.dll` 和 cuDNN 9（自带的 `cudnn64_9.dll` 只是加载器，真正的子库要另装）。`ctranslate2.get_cuda_device_count()` 照样返回 1，可是一识别就报 `Library cublas64_12.dll is not found or cannot be loaded`。按 README 原来的写法，要再装 CUDA Toolkit 12（约 3 GB）和 cuDNN 9（要注册 NVIDIA 账号才能下载）。

**做法**
- 和用户商量后改用 pip：`nvidia-cublas-cu12` 和 `nvidia-cudnn-cu12` 只装进 `.venv`（约 1 GB），不动系统，也不和已经装的 CUDA 13 冲突。
- 这两个包把 DLL 放在 `site-packages\nvidia\*\bin`，Windows 默认不去那里找。`FasterWhisperBackend.load()` 在导入 faster-whisper 之前先把这些目录加到 `PATH` 前面；没装这两个包时什么都不做，系统装的 CUDA 12 照样能用。
- 试过只用 `os.add_dll_directory`：不管用，ctranslate2 第一次用显卡时才按 `PATH` 去加载 cuBLAS。所以只改 `PATH`。
- 没有写进 `requirements.txt`：只用 CPU 的人和 CI 不需要多下 1 GB。README 第 3 步改成这条 `pip install`。

**主要文件**：`simul_interp/asr/faster_whisper_backend.py`、`README.windows.md`

## S29 · Windows 实测：内录时点“退出”程序崩溃（2026-10-14）

**问题**：界面测试时用户点了“退出”，窗口都关了，进程却还在，过了一阵才结束，退出码不是 0。用音频文件模拟时退出正常，只有内录时出问题。

**排查**
- 写了一个小脚本，内录模式下 10 秒后自动调用 `app.quit()`，给 `WindowsLoopbackSource.stop()` 和 `_close()` 的进出计时，开着 `faulthandler`。复现了：退出码 `0xC0000005`（访问冲突），之前还报了 `0xC0000374`（堆损坏）。
- 计时显示 `stop()` 在 10 毫秒内被调用了两次，来自两个线程：主线程退出时的 `Pipeline.stop()`，以及识别线程收尾时 `AsrRunner.run()` 的 `finally: source.stop()`。两边同时关同一个 PortAudio 流，重复释放，把内存搞坏了。
- macOS 内录的 `stop()` 只是结束辅助程序再等线程，调用两次没关系，所以 Mac 上一直没暴露；文件音频源也一样。
- 单独的脚本（边播放边连续 `reconnect()` 10 次，再从两个线程同时 `stop()`）同样在 `stream.close()` 里崩溃；`reconnect()` 本身没问题。

**做法**
- 新增一把只管打开 / 关闭录音流的锁 `_device_lock`，`stop()` 只有第一次真正去关，第二次直接返回。
- `reconnect()` 也改用这把锁，不再拿 `_feed_lock`：关流要等正在执行的回调结束，而回调要拿 `_feed_lock`，用同一把锁有互相等待的风险（实测没碰上，但没必要留着）。停止以后再点“重新连接”什么都不做，不会把流重新打开。

**主要文件**：`simul_interp/audio/windows_loopback.py`、`tests/test_windows.py`

**验证**
- 新增单元测试：两个线程同时 `stop()`，只关一次；停止以后 `reconnect()` 不再打开；音频流正常结束。修复前这个测试失败，修复后通过。pytest 共 128 个通过。
- 实机：自动退出脚本跑两次，退出码都是 0，从点退出到进程结束约 0.2 秒；`reconnect()` 10 次加两个线程同时 `stop()` 的脚本，退出码 0。

**经验**：关闭原生资源（音频流、设备句柄）的函数要能安全地重复调用，尤其是“正常结束时自己关、用户退出时别人也来关”的情况。Python 对象关两次通常只是报个错，C 库关两次会直接把进程弄崩，而且崩溃点和原因离得很远（这次表现为退出卡住、退出码异常，日志里什么都没有）。

**杂音里的 “Merci.”（S15）**
- 合成了 40 秒的键盘敲击、提示音、闷响，走完整流程：语音检测一次都没触发，自然也没有 “Merci.”。合成的杂音太“干净”，检验不到核实这一步。
- 于是跳过语音检测，直接对 85 段杂音（键盘声、提示音、白噪声、低频噪声，各 1～2.5 秒）识别：37 段的结果是 “Merci.”，复现了 S15 的问题；这 37 段的 `word_probability` 最高 0.43，全部低于阈值 0.7，都会被过滤。
- 从 `fr_meeting.wav` 按参照里的逐词时间剪出一个单独的 “Merci”：核实 0.94、0.93，照常显示。每次核实耗时 0.37～0.61 秒，单独一句 “Merci.” 会因此晚出现约半秒（交接文档里的可疑点，属实但可以接受）。

**交接文档里其他可疑点**：切换输出设备确实不会自动跟随，手动重新连接可以恢复（另外用脚本边播放边连续重新连接 10 次，都正常）；控制台编码没有问题，不用设 `PYTHONUTF8`；半透明窗口和文字阴影在这台机器的本地显示上正常，没有测远程桌面。

**做法**：README.windows.md 去掉“尚未在实体机上验证”的警告，常见问题加一行 symlinks 警告；`CLAUDE.md`、交接文档和两个 Windows 模块的文件说明里“没有在实机上运行过”的说法改成实测结果。

**验证**：上面的清单；pytest 128 个通过。

**经验**
- 退出流程最容易只在真机上出问题：单元测试不会真的打开音频设备，CI 也不会点“退出”。这次唯一的崩溃就在这里（S29）。
